# Streamline FG and native NGX Vulkan coexistence probe

This is an **experimental, standalone Windows x64 Vulkan probe** for native NGX DLSS SR alongside Streamline DLSS FG. Its `CMakeLists.txt` is the entry point; the game's root CMake does not include it. The probe implements a small synthetic scene and FG off/on/resize and retirement sequences. It is not production FG integration, and **P0 Gate 1 has not passed**.

It needs the official Streamline v2.14.1 SDK described in `sdk-manifest.json`, a separate local NGX 310.9.1 SDK, and Visual Studio 2022 with CMake 3.28 or newer. Configure does not download either SDK. The build copies only the required Streamline runtime DLLs from the local SDK and the native NGX SR runtime from `LoDlss.cmake`; `sl.dlss.dll` must not be placed beside the executable. SDK archives, headers and binaries remain outside this source checkpoint.

From the repository root in PowerShell, after placing the SDKs in the local `.cache/deps` paths:

```powershell
$manifest = Get-Content tools/tests/streamline_fg/sdk-manifest.json -Raw | ConvertFrom-Json
$zip = '.cache/deps/streamline-v2.14.1/streamline-sdk-v2.14.1.zip'
if ((Get-Item $zip).Length -ne $manifest.asset_size -or
    (Get-FileHash $zip -Algorithm SHA256).Hash.ToLowerInvariant() -ne $manifest.asset_sha256) {
    throw 'Streamline SDK archive does not match sdk-manifest.json'
}
# Extract the verified archive so its include/ and bin/x64/ directories live under .cache/deps/streamline-v2.14.1/sdk/.
cmake -S tools/tests/streamline_fg -B out/streamline-fg-p0 -G 'Visual Studio 17 2022' -A x64 -DLO_STREAMLINE_SDK_ROOT="$PWD/.cache/deps/streamline-v2.14.1/sdk" -DLO_ENABLE_DLSS=ON -DLO_REQUIRE_DLSS=ON -DLO_DLSS_SDK_ROOT="$PWD/.cache/deps/nvidia-dlss-37495948"
cmake --build out/streamline-fg-p0 --config Release --target LoStreamlineFgProbe --parallel 2
```

The SDK manifest pins the release ZIP by size and SHA-256; the CMake helper also fails when its required headers or DLLs are missing. NGX SDK discovery and its native SR runtime are checked by `LoDlss.cmake`. This standalone build does not build the game or turn on an FG production path.

For a separately authorized manual hardware diagnostic, run `out/streamline-fg-p0/Release/LoStreamlineFgProbe.exe` from a dedicated results directory, or pass `--no-activate` for a nonactivating borderless window. The probe prints requested and actual client/surface extents. Exit code 0 means its bounded sequence completed on the tested hardware; 77 indicates an unavailable capability or environment (including an unfocused background window without generated presents); 1 indicates failure, including cleanup or Vulkan validation errors. A zero exit alone is not physical-display or P0 Gate 1 acceptance evidence. SDK state, hook counts and captured host images are not generated-frame captures.

The opt-in `--explicit-input-wait` mode is a diagnostic for Streamline configurations using `eBlockNoClientQueues`. It adds explicit timeline waits before input resource reuse/destruction for frame, mode-change and drain paths; it leaves the default mode unchanged. Before `vkQueuePresentKHR`, an unknown completion state is not treated as complete: only a valid `GetState`/fence result can enter pending completion, while failed waits abandon the input. Cleanup snapshots session counters before teardown and reports cleanup increments separately from session errors; any error still fails the run. `GetState` must be used from the present thread, and this mode does not establish the root cause of SDK or callback-stage errors.

The probe and CPU option-parser test built successfully, and the CPU test passed. After the run below, source-only logging was moved before the completion-fence guard and `FG_INPUT_FENCE_STATE` was added to distinguish a null fence from a zero value; that logging-only edit has not been rebuilt or run. The frozen executable and source patch in the results directory preserve the tested version. The synchronization contract is documented in the [pinned SDK guide](https://github.com/NVIDIA-RTX/Streamline/blob/2122257e0fce486f91b385aa63b9a09b0a34b363/docs/ProgrammingGuideDLSS_G.md#151-how-to-synchronize-the-host-app-dlss-g-inputs-and-streamline-if-required).

### Official Streamline sample reproduction

The official Streamline `v2.14.1` sample (tag commit `0bb8bf3ee80ce8d6b53688c2e237ac0981ce2f6c`) was built independently. The first debug run changed only CMake configuration, left runtime code unchanged, and crashed with `0xC0000005` at `exe+0x421b`; the isolated [minimal validation patch](official_sample_validation.patch) additionally fixes the validation-wrapper device lookup, missing `independentBlend`, `privateData`, and `deferred_host_operations`. The patched build exited 0 (SHA-256 `1445D1CD3E490BBBEA909F2492AA5AA04F55BD5BD7C708CB00F02A0816A5441E`), and `-vk -debug -sllog -logToFile -DLSSG_on -maxFrames 100` in `out/streamline-sample-v2.14.1/run02-minimal-fix/` also exited 0. Its log reports interpolation enabled at line 1066, clone `UNDEFINED` versus expected `TRANSFER_SRC` at lines 1112/1114, and pacer semaphore reuse at line 1124. Sample-specific GBuffer-clear and teardown errors are separate. This is reproduction evidence, not a validation-clean generated frame, physical-display acceptance, or proof of an SDK/host fix; the first CMake-only sample crash remains part of the baseline.

The bounded run in `out/streamline-fg-p0/explicit-input-wait-20260926/run01/` used executable SHA-256 `D5A9DE18ECC1C7DF0346266CB079D30512E9C315FFC1F7EB0F99B59BFDEE1660` with `--no-activate --explicit-input-wait`. Three FG-off frames completed; the first FG-on frame failed because `FG present did not return an input processing completion fence/value`. Session validation and Streamline error counts were both zero, but cleanup remained `LIFECYCLE_CLEANUP_OK=0` with an abandoned input and no fence wait executed. No FG-on `FRAME` state line was recorded, so generated or physically presented frames cannot be claimed. The manifest preserves a null OS exit code; this run was not a foreground retry and Gate 1 remains **NOT PASSED**.

Earlier local evidence in `out/streamline-fg-p0/` is limited to those specific builds and runs. The `gate1-codex-background-03` manifest records an older binary (`366657...`) with no generated presents. Foreground/background comparisons used another binary (`c13bdc...`): the foreground run reported `actual_presents=2` in FG-on intervals, but both runs exited 1 because validation reported layout/synchronization errors (`p0-foreground-sync-audit.md`). A later foreground API-dump run used binary SHA-256 `f47431b7746cdf54d847d7008547c0d7af0bce8a579f7596cccd5d95334c9efa` (`gate1-codex-apidump-01/manifest.json`), again reported generated intervals and exited 1. The captured first SDK pacer layout mismatch and R16F write hazard are documented in `p0-api-layout-trace.md` and `p0-host-remediation-followup.md`; their diagnosis does not validate the remaining hazards or demonstrate a host-side fix. None of these runs establishes a validation-clean generated frame or physical display. P0 Gate 1 remains **NOT PASSED**.

Current source includes a host-side Gate-1 remediation candidate: the Streamline proxy swapchain image is left in `VK_IMAGE_LAYOUT_TRANSFER_SRC_OPTIMAL` when control enters the hooked `vkQueuePresentKHR`, instead of being transitioned by the application to `PRESENT_SRC_KHR`. This directly targets the previously recorded pacer-layout VUID. Treat this as an experiment supported by the earlier trace, not as an established SDK or pacer contract. The foreground run in `out/streamline-fg-p0/pr69-foreground-20260926/` used executable SHA-256 `8b4d456b8754e320845f5801d22278933030b77db6437c0dfa1ccdda37f1670c` and covered 48 frames with 33 FG-on `actual_presents=2` intervals, 32 validation callbacks, and exit 1. Its historical aggregate `LIFECYCLE_CLEANUP_OK=0` folded the 32 validation and 32 Streamline errors into cleanup accounting; it does not independently prove that a teardown API failed. It logged RAW/WAW and threading hazards, SDK clone outputs with expected `TRANSFER_SRC` but actual `UNDEFINED`, pacer semaphore reuse, and wait-order cases; the duplicate cap was 10. The old host proxy layout mismatch was not observed, and the same SDK clone/layout classes appeared in earlier evidence, so no new regression or single confirmed cause is claimed. No external-display evidence exists; Gate 1 remains **NOT PASSED**.
