# Lost Odyssey Profiling

把性能问题收敛到可复现的测量、可解释的热点和有证据支持的下一步。默认使用简体中文交付。用户只要求诊断时，完成诊断和证据交付，不自动实施优化。

## 选择测量方式

先复用当前任务的采集、构建身份和已通过验证，核实易变的进程与运行条件。明确要解释的是帧卡顿、CPU 执行、线程等待、GPU 时间还是具体指令热点；不把一种测量冒充另一种。

- 已有 capture：先离线分析，只有缺失的证据会改变结论时才补采。
- CPU 执行热点：优先使用环境已有的 on-CPU 采样和符号能力。wall-clock 线程快照用于定位停留位置，包含睡眠／等待。
- 帧卡顿：关联帧间隔分布与同一时间窗口的 CPU／GPU／提交等待；平均 FPS 不能解释尾部卡顿。
- 汇编热点：结合运行中的 host 指令、模块、符号和构建身份。优化后的源码行号是近似归因，静态汇编不能证明运行耗时。
- LostOdysseyRecomp：读取 [专用采样流程](references/lost-odyssey.md)，复用仓库 `tools/asm-profiler`；不要再写一套临时采集器。
- 其他项目：遵循其已有工具和构建流程，不假定存在 LO 工具或可用的 ETW、硬件计数器、GPU 分析器。

## 测量与归因

记录足够复现本次结果的身份和条件：目标 EXE 路径／SHA256、PID／创建时间、源码或构建版本、符号来源、实际采集时长、场景／存档标识、后端／分辨率／画质／限帧，以及会影响比较的前后台状态。根据任务选择必要项；不复制用户存档到公开报告。

采集前检查是否已有正在运行且身份匹配的目标。请求 profiling 通常授权必要的范围内采集，不反复确认；启动、读档、前台交互仍按当前会话授权和项目规则执行。LO 后台测试不抢焦点，非音频实验使用测试专用静音配置，保留用户设置。缺少必要交互安排时先完成离线工作，再说明具体缺口。

使用有界采集窗口和独立输出路径。保留原始 capture，不为筛选线程或改变展示重复采集。发生权限失败、空样本、目标退出或恢复线程失败时，先核对明确失败原因；不要用连续重试代替诊断。

解读时区分：

- **样本占比**：分母是什么，是否包含等待、未知符号和被筛除线程。
- **线程 CPU 时间**：OS 计时的观察区间增量，不能按 wall 样本占比分摊到指令。
- **函数 self 与 inclusive**：没有调用栈就不声称得到 inclusive 时间或调用路径。
- **汇编上下文**：命中的 RIP 与后续展示指令不同；相邻指令没有因此被采样。
- **GPU／等待**：CPU 在 wait 函数不能单独证明 GPU 饱和；GPU 利用率也不是每个 pass 的计时。
- **指令事件**：没有相应测量，就不能给出 cycles、cache misses、branch misses 或逐条指令延迟。

无符号样本保留并报告覆盖缺口；模块 ASLR 比较优先使用模块身份＋RVA。检查符号／源码与实际 EXE 是否匹配，不通过函数名猜测精确 guest PC。

## 对比与收尾

对比保留基线，只改变要研究的变量，保持场景、窗口、限帧和采集方式可比。记录采集开销和无法控制的差异；条件不匹配的结果标为探索性。只在证据能支持时给出因果或收益结论，不把热点占比直接换算成可回收毫秒或 FPS。

交付原始证据位置、可读报告、构建身份、主要热点与限制，并指出最小的后续验证或修改方向。区分工具可用、合成验证、游戏实测、用户验收与发布。已有测试仅在具体变化使结论失效时重跑受影响部分；提交、文档同步和重新打包本身不构成重测理由。

仓库要求 Project／文档同步时按其流程处理；skill 不自行授予提交、发布或扩大开发范围的权限。
