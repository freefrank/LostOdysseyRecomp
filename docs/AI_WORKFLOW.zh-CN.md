# Recomp 的 AI 协作工作流

[English](AI_WORKFLOW.md)

日期：2026-10-18

本文总结《Lost Odyssey》重编译移植（LORecomp）在 2026 年 9 月到 10 月的工作方式。那段时间，一名维护者带着 AI 编程助手做开发：Claude Code 作为主会话，Codex CLI 和多个 subagent 负责具体工作。本文分享流程、subagent 规则，以及移植其他 Xbox 360 游戏时容易踩的坑。工程取舍见[工程原则](LORecomp_ENGINEERING_PRINCIPLES.zh-CN.md)。

## 1. 分工

| 角色 | 负责 | 不做 |
|---|---|---|
| 维护者 | 定方向、做决定；用眼睛判断画面问题；试玩和验收；发 Reddit/Discord 等公开帖子 | 不当流程闸门，日常决定交给主 agent |
| 主 agent（Claude Code 主会话） | 和维护者沟通；拆任务、写交接 prompt；审 diff 和证据；合并、发版、回复 issue；写记忆 | 不亲自做长时间的调查和构建 |
| Codex CLI | 长任务：静态审计、实现加构建、远程主机上的复现和压力测试 | 不合并、不发版，结果交给主 agent 审 |
| Claude subagent | 短的并行任务：查代码、查文档、机械改动、文档同步、看板同步 | 不再委托别人，不越出交给它的范围 |
| 测试主机 | AMD 掌机（Linux，Proton D3D12 / 原生 Vulkan）、Mac、Android 平板、Switch/PS5 实验机 | 本机只在允许时跑游戏 |

维护者给了主 agent 完整权限：权限范围内的事直接做，做完报告。只在三种情况下停下来问：操作有破坏性，影响对外，或者权限不够。

## 2. 基本原则

- **运行效率第一。** 这是业余项目，不加企业级的测试、校验和防御代码。变化在源头检测，不做每帧轮询或重复哈希。修 bug 时优先删掉多余的工作，而不是再加一个开关。
- **出厂默认等于原版。** 原版是 720p30，所有增强都要玩家自己打开。测试用的分辨率写在配置文件里，不改代码。原版本来就有的行为（比如远景淡出）不当 bug 修。
- **结论要有证据。** 实现、验证、验收、发布是四件事，分开记录。发布不等于验收，CI 全绿也不等于游戏能跑。
- **逻辑通顺就可以发。** 难复现的竞态，写清楚“持锁期间双方各在做什么”的论证就够了，不必非等复现。但不能把片面的测试当成完整验证（见第 7 节）。
- **对外文字要短。** 写给玩家看的，不放测试数据。定稿前再改一遍，去掉 AI 腔。
- **不加 AI 署名。** commit、PR、issue 和评论里都不写 Co-Authored-By 或 “Generated with”。

## 3. Subagent 与 Codex 的使用规则

### 3.1 角色表

| 角色 | 用途 | 模型 | 权限 |
|---|---|---|---|
| explorer | 定位代码、追调用链；要读很多文件但只要结论时用 | Sonnet | 只读，有 CodeGraph 就先用 |
| researcher | 外部库、API、工具的文档和发布说明 | Sonnet | 只读，查文档先用 ctx7 |
| worker | 规格清楚的机械改动、写脚本、跑构建 | Sonnet | 可写 |
| docs-sync | README 双语对、CHANGELOG、STATUS/ROADMAP、发布记录 | Haiku | 只改文档，不提交、不推送 |
| project-manager | GitHub Project 看板和 TODO 同步 | Haiku | 只改看板和 TODO |
| general-purpose / Plan | 调试、复核、做方案 | 显式指定 Opus | 视任务而定 |
| Codex（`codex exec`） | 长调查；实现、构建、远程测试 | 显式指定模型 | 在独立 worktree 内拥有完整权限 |

### 3.2 模型与数量

- 不继承父会话的模型。自定义 agent 用它定义里的模型，内建 agent 每次都显式写 `opus` 或 `sonnet`。
- 同时跑的 agent 控制在个位数，不做没有上限的 fan-out。教训：有一次给每条发现都配一个验证 agent，结果开了一百多个，直接耗光额度。
- Claude 周额度紧张时，长任务交给 Codex，主会话只负责审查。开大任务之前先查一下用量。

### 3.3 什么时候委托

适合委托的：
- 几块彼此独立、可以并行的工作；
- 要读很多文件、但只需要结论的搜索；
- 跑很久的构建、测试、巡游；
- 需要远程主机的复现。

不委托的：
- 一两步就能做完的小事；
- 紧密耦合、需要反复来回修改的工作；
- 已经交出去的同一件事。

主 agent 默认只做这些：沟通、拆分、审查、合并、发版，以及很小的即时操作。

### 3.4 交接 prompt 怎么写

一份能独立执行的 prompt 至少包含：

1. **工作目录**：一个独立的 worktree 和它的基点提交。不能碰主 checkout，也不能放在同步盘里。
2. **目标**，以及怎样算“做完”。
3. **已有证据**：日志路径、复现条件、已经排除的方向。
4. **线索**：可能相关的文件、函数、地址，并注明哪些只是推测。
5. **规则**：测试主机的规则（锁、只停自己的进程）、本机能不能跑游戏、不能推哪个 remote、不能改哪些配置、不加 AI 署名。
6. **验证要求**：要编译到哪一步、要不要完整链接、要跑哪些测试。
7. **交付**：报告的路径和语言；开不开 PR。默认开 ready PR，但不合并。

附录有一份模板。

### 3.5 审查是主 agent 的事

subagent 的报告是输入，不是结论。主 agent 必须自己读 diff，逐条核对证据。这段时间实际抓到过的问题：

- docs-sync 把旧版本里的修复，写成了新版本发布的内容。
- Codex 改了设置项的键名，但漏改了 Android 端读取这个键的代码。
- 一个 PR 的 CI 全绿，合进去后 main 却链接失败：新 hook 和已有 hook 重复定义了同一个函数，而 PR 的 CI 根本不链接最终的 exe。
- 一个加锁的修复只做了强制复现的对照就合并了，结果在自然压力测试的第 79 次出现死锁（第 7 节）。

### 3.6 监视与改方向

- Codex 跑在一个看得见的终端标签里，维护者随时可以按 Ctrl-C 停掉。日志和最终消息都写到文件里。主 agent 再开一个后台 watcher，看到结束标记就收到通知。
- 不用长时间阻塞的轮询。CI 和发布构建也交给后台命令，跑完自动通知。
- 方向变了，就停掉任务，带上新指令恢复原来的会话（`codex exec resume`），不要另起一个。
- 共享的远程主机上，可能同时有多个任务在排队等锁，主 agent 要协调好顺序。

## 4. 从 issue 到发布

### 4.1 分诊

- 先把附件下载到本地的 `_keep/<issue>/`，从头到尾读完整的日志。
- 同类报告排成一张表，列出每次崩溃是“进入哪张地图、哪场战斗或哪段视频之后几秒”，再跨玩家、跨版本找共同点。比如五份 DEVICE_REMOVED 报告：全都是 NVIDIA + D3D12 + 4K + 4x 贴图包，其中两份崩在同一场下水道战斗开始后约 2.4 秒。
- 自动分诊机器人只是起点，它常常把不相干的 issue 关联在一起。
- 证据不够时，请玩家附上调试日志和存档。调试日志现在默认开启，D3D12 的 DRED 也跟着开。

### 4.2 定位

- 有 CodeGraph 就先用它，不要对整个仓库根目录 grep。
- 静态审计交给 Codex。要求它给出每个释放、复用或覆盖点的 file:line，并说明有没有 fence 或锁保护。
- 不靠反汇编器的逆向技巧：
  - 生成的 PPC 代码每条指令都带一行注释，地址 = 函数起点 + 4 × 指令序号。
  - 从镜像里的 UE3 natives 表找类和函数；比较子类和父类的 vtable，找出被覆盖的方法。
  - 用硬件写断点（DR0–DR3）抓到谁写了某个地址，再沿 r1 回溯 guest 调用栈。
  - 先用逐帧 trace 给问题分类，比如摄像机位置平滑、朝向乱跳，说明是游戏逻辑的问题而不是渲染。

### 4.3 复现

- **本机运行**：只在维护者允许时跑，而且用维护者自己的安装。跑之前加锁、备份要替换的文件并记下哈希；跑完按哈希还原。日志写到另外的目录，不让游戏清掉玩家原有的日志。
- **共享测试机**：所有运行都持锁。只停自己的进程，按 `/proc/<pid>/cmdline` 里的运行路径认。不用 `pkill -f`。命令写进 `.sh` 文件，不把 exe 路径放在 ssh 命令行上。
- **画面问题**：前台运行，停在固定场景，一次只改一个变量，说清楚屏幕上现在是哪个配置，等维护者用眼睛判断。自动指标和肉眼冲突时，以肉眼为准。先确认是否只在某个显卡厂商上出现，再去逐版本二分。
- **剧情后期的场景**：用诊断跳图、换盘请求和 Scenario Jump 造测试存档，不碰玩家的存档。
- **难复现的竞态**：用诊断开关强行把时间窗口拉长。但强制复现只能证明旧的竞态修好了，证明不了新加的锁不会死锁。

### 4.4 修复

- 每个任务一个 worktree，放在同步盘之外。
- 跟周围的代码保持一样的写法，改动尽量小，性能放在第一位。
- **Hook 规则**：
  - 加 `PPC_FUNC(sub_X)` 之前，先查有没有人已经 hook 过同一个函数。有的话，在现有 hook 里调用你的逻辑，不要再定义一个。
  - 改了 midasm hook 的 TOML，要重新生成 PPC 代码。
  - PR 的 CI 不链接 exe，所以凡是加 hook 的改动，合并前都要在本地做一次完整的 Release 链接。
- **锁**：锁里不调用任何 API，也不做任何等待。合并前写清楚持锁期间双方各在做什么。

### 4.5 验证

- 验证的分量要和改动的影响相称。默认跑一次冒烟测试，矩阵测试只在有人要求时做。保留基线、控制变量，比较时用 ABBA 的顺序。
- 测试跑完再下结论。“没复现”不等于“修好了”。

### 4.6 PR 与合并

- 开 ready PR，审完 diff，等必需的 checks 全部通过再合并。用 squash 合并，并带上 `--match-head-commit`，确保合进去的就是审过的那个提交。不绕过分支保护，不 force-push 共享分支。
- 只改文档或只改字面值（版本号等）的 PR，审完 diff 就可以合。
- 往一个分支推送之前，先确认对应的 PR 还开着。维护者合并得很快，晚一步推上去的提交就会落在一个已经合并的分支上。

### 4.7 发布清单

1. **发版 PR**：把 CHANGELOG 的 Unreleased 改成版本标题（日期用 UTC，确认后再写），同时改 CMake 版本号和安装文档里的文件名。
2. **打 tag**：在 squash 提交上打 annotated tag，只推到 origin。
3. **构建**：GitHub Actions 构建全部安装包并自动发布，主 agent 在后台等，不轮询。
4. **核对**：资产数量、大小，以及发布说明是否和 CHANGELOG 对应的那一段一致。
5. **记录**：更新包管理清单（`.forge.json`），由 docs-sync 写发布记录（STATUS/ROADMAP/MACOS_RELEASE），走一个记录 PR。
6. **通知**：相关 issue 下各回一行发布链接，等玩家确认后再关。
7. **记忆**：更新 Basic Memory 的发布快照和本地记忆。

发现回归时：马上 revert 并发新版本，然后对外说明。不要再叠一个没验证过的修复上去。

## 5. 对外沟通

- **Issue 回复**：一两句话，说改了什么、什么时候能拿到。不放测试数据，只问真正需要的信息。
- **CHANGELOG**：每条一行，写玩家能看懂的话，不写证据。
- **README**：写给玩家看，不写验证历史和内部细节。
- **公开帖子**：由维护者自己发，agent 只写草稿。

## 6. 记忆与记录

| 层 | 存什么 | 规则 |
|---|---|---|
| 仓库文档 | 技术证据、当前状态（STATUS/ROADMAP/CHANGELOG/notes） | 过时的文档用 `git mv` 移到 archive，并修好链接 |
| Basic Memory（跨工具共享） | 结论和方法：项目索引、发布快照、待跟进事项、Issue 根因台账、主题笔记 | 易变状态只写进快照和待办这两篇，带日期和来源；写之前先搜，已有的主题追加带日期的小节 |
| 本地 agent 记忆 | 工具习惯、维护者的偏好和纠正 | 一件事一个文件，外加一行索引；索引过长就合并精简 |

- 会话开始时，hook 提醒先读记忆；合并或发版之后，hook 提醒写记忆。
- 不存密钥和凭据。

## 8. 移植其他 Xbox 360 游戏时的常见坑

### 8.1 重编译与构建

- **内存屏障**：PPC 的 `lwsync`/`sync`/`eieio` 必须在生成的代码里变成真正的内存屏障。从旧目录复制来的 PPC 源文件可能没有，ARM 上会出现莫名其妙的崩溃。怀疑 guest 代码之前，先确认生成的代码是新的。
- **Hook 重复定义**：同一个 guest 函数只能有一个 `PPC_FUNC` hook。CI 不链接的话，重复定义会一路漏到发版时才暴露。
- **midasm hook 要重新生成**：只改 TOML、不重新生成 PPC 代码，hook 根本不会生效。
- **函数指针别写死**：有些全局量其实是指针（例如 `*0x832D268C`）。拿 r3 去和地址常量比较的 patch 会静默失效，永远不触发。
- **私有输入不提交**：XEX、生成的 PPC 和游戏数据都不进仓库。CI 通过 deploy key 拿私有输入。

### 8.2 内核与 XAM

- **异步完成太快**：模拟层的 XAM、IO 往往立刻完成。游戏原本靠真机上的耗时掩盖了自身的竞态，到这里就会暴露出来（#615：完成信号被随后写入的“忙”状态覆盖）。修的时候锁要尽量小。
- **critical section**：字段是大端存储。持锁时调用任何会等待其他线程的东西，都可能死锁。
- **import bridge 会暂停**：guest 线程可能在 import 入口被 host 菜单暂停。锁的进入和退出要避免经过这种暂停点。
- **抄 Xenia 的 stub 要先看看**：Xenia 为某个游戏加的 sleep，在别的游戏里会把音频线程卡到每秒 82 次。
- **XMA**：解码返回 -11 是真的拒绝了那一帧，不代表“需要更多数据”。
- **存档内容**：存档文件夹名就是内容名。崩溃后元数据可能是全零，要以实际的存档数据为准。

### 8.3 内存

- **页大小**：Apple Silicon 和 PS5 是 16 KiB 页，表达不了按 4 KiB 偏移的物理别名。做法是不映射那个视图（E），按地址算出物理地址，不改 PPC 语义。
- **4 GiB 窗口**：guest 地址空间最好落在首选基址上，各平台的预留方式不一样，要逐个验证。

### 8.4 GPU 与渲染

- **时间性闪烁**：TAA、DLSS、FSR 下的闪烁，几乎都出在某个没有加 jitter 的 pass。只要在任一时间性 AA 上修好，其他的也会一起好。
- **后处理贴图偏移**：shader 按 guest 贴图尺寸计算 texel 偏移，所以内部分辨率调高后，后处理的覆盖范围还停留在 720p 的尺寸。
- **资源生命周期**：
  - 释放必须等 GPU fence。
  - 绘制中途换了 GPU 批次，已经拿到的描述符集就不能再用。
  - 以裸指针为键的缓存，地址被复用后会命中旧对象。
  - 这三类问题都会表现为 DEVICE_REMOVED。
- **调用常量要传全**：比如 blend constant 漏传，敌人就不会淡入。
- **驱动差异**：
  - AMD 驱动层的超分（RSR、FSR 升级）会弄坏 Vulkan。
  - Adreno 的系统驱动只支持 Vulkan 1.1，要用 Turnip。
  - Turnip 上 `vkGetFenceStatus` 会阻塞等待，Android 上不要轮询 fence。
- **着色器**：首次使用时编译会造成卡顿。预编译包要有版本契约，契约不匹配就会全部回退成现场编译。

### 8.5 游戏逻辑与高帧率

- **固定步长的重采样器**：按 12.5 ms 等固定步长重采样的逻辑，每步最多只吃一条历史，帧时间短于步长就会出错（战斗摄像机乱转）。
- **按帧计数的计时器**：高帧率下会走得更快。
- **固定的提示停留时间**：可以安全缩短，但要先确认后面的阶段会自己等异步结果，不依赖这段停留。

### 8.6 平台与输入

- **libc++ 的带超时等待**：Android 和 macOS 上，带超时的信号量等待会每 8 ms 醒一次。长期运行的线程不要用超时等待。
- **手柄按键交换**：SDL3 配合 Steam Input 时，Nintendo 布局的手柄会被交换两次。
- **签名**：macOS 包没有 Developer ID，Android 包一直用 debug 签名，安装说明里要写清楚。

```markdown
# <issue 号>: <一句话目标>

仓库：<owner/repo>。工作目录：<独立 worktree>，分支 <branch>，基于 <commit>。
不要改主 checkout，不要放进同步盘。

## 证据
- 日志：<路径>；复现条件：<…>；已排除：<…>

## 线索（推测，需要核实）
- <文件:行 / 函数 / 地址>

## 要做的
1. <步骤>
2. 修复只针对已经证明的原因，改动最小，跟周围代码写法一致。

## 规则
- 测试主机：持锁；只停自己的进程；不用 pkill -f；本机不跑游戏。
- 不推 <remote>；不改 <配置>；不加 AI 署名。

## 验证
- 编译 + 完整链接；<测试或运行>。

## 交付
- 中文报告写到 <路径>：结论、file:line、证据、还没验证的部分。
- 开 ready PR，不合并。
```
