## Findings

The strongest concrete implementation candidate is the texture-cache hash distribution. `TextureKeyHash` combines the guest address, format, width, height and flags before selecting one of 512 buckets. Guest addresses are 4 KiB aligned; because the bucket mask is 511, it retains only the low nine hash bits, while the low twelve address bits are zero, so the address term does not mix higher address distinctions into bucket selection. A live, read-only cache snapshot at 17:09:42 found 386 keys, 33 non-empty buckets, and a longest chain of 84. All 84 entries in that chain shared format 18, 128x128 dimensions and flags 20515 while differing in address. The renderer pointer, map metadata, bucket array, list counts and per-key bucket placement were mutually consistent. This confirms a structural distribution defect, but not that it alone explains the missing 60 FPS. An existing ETW hotspot attributes 318/10,848 render samples (2.9314%) to the repeated chain and 323 (2.9775%) when bucket selection is included; the latter contains the former.

`memcmp` accounted for 766 render self samples (7.0612%). Its callers were vertex sample checking (376, 3.4661%), `UploadUnchanged` (226, 2.0833%), shader-identity caching (132, 1.2168%) and texture descriptors (32, 0.295%). The existing 64-byte path is already inline SIMD. The vertex comparison has two branches: nonzero lengths up to 8192, except the 64-byte SIMD case, use whole-block `memcmp`, while longer lengths use 512-byte head/tail `memcmp` checks plus 64 internal 64-byte SIMD windows. Reducing it must preserve content-change and collision correctness. The inclusive vertex `Visit` total was 795 samples (7.3285% of render samples) and must not be added to the 766 self count. Constant-upload caller values were parameter lengths in bytes: 4096, 4096 and 1024; the 1024 value is the actual instruction-parameter size.

The evidence supports the conclusion that this is a static PPC-to-C++-to-native recompilation pipeline with ordinary native hotspots, rather than an interpreter-dispatch bottleneck. Only 22 of 54 complete hot-function matches had unique machine-code correspondence, with 13 additional semantic attributions; the runtime had no CodeView data, so these are bounded mappings rather than release-PDB proof. Guest-thread analysis places all 6,223 guest-render samples under `sub_824856A0` (the existing RenderingThreadMain semantic name), with 4,974 (79.93%) under `sub_825B2A20` (FSceneRenderer::Render). Thread 12824 has 4,301/4,474 samples (96.13%) under `sub_82290D28`. The observed leaves cover command construction, geometry and particle distribution; their measured coverage was 337/6,223 (5.42%) on TID 43848 and 441/4,474 (9.86%) on TID 12824, so polling costs remain unexcluded without generalizing the leaf identities.

The source audit records default guest occlusion-query feedback as synthetic visibility, which may add draws; the additional draw count was not quantified. During the first 32 rounds the guest continues polling; after that, a known host hook yields with a timer. D3D12 fence waiting is a separate blocking path. Blocking waits alone do not establish a CPU busy-spin defect; the cost of guest polling remains unquantified. The DB16CYC code-generation no-op remains a source candidate and was not measured as the main cause.

## What remains unknown

The observations do not provide a controlled 1080p-at-60 benchmark, GPU per-pass timing, exact busy-wait coverage, or a clean CPU/GPU A/B at a recorded power limit. The 40 W package limit and 4K internal workload simultaneously constrain CPU and GPU headroom. The next implementation candidates are, in order, correcting texture-hash distribution, reducing redundant per-draw checks while retaining correctness, and measuring real occlusion culling. No candidate has been implemented or assigned an FPS prediction in this record.
