# v0.8.0 P0、P1、P4 开发交接

日期：2026-09-27。本文面向后续开发和验证，基线为本轮起点 `88b1a4b`；当前验证分支为 `trail/fg-checked-validation-20260927`，基于 `03b5b117`。它把当前实现、证据边界和可执行任务集中到一处；不改变路线图中 P0、P1、P4 的里程碑定义。

## 目标与非目标

本阶段的目标是：

- 收敛 P0 共同时序契约在真实游戏路径中的 SDK 同步、输入完成和会话生命周期证据，并完成 Gate 1 所需的验证闭环。
- 保持 P1 已验收的独立 FSR SR 所有权和输入契约，继续保证质量档位、Native AA、尺寸变化、reset 与 fallback 语义。
- 在 Windows Vulkan 上推进 P4 固定 2× DLSS FG，覆盖 DLSS Quality+FG、DLAA+FG、FSR+FG，并验证 feature probe、状态切换、暂停恢复、切场景、电影和窗口变化。

本阶段不包括独立 FSR FG、D3D12 FG、动态 MFG、原生 120 FPS、Linux AArch64、macOS AArch64 或 Android 交付。P4 也不把 OSD、`actual_presents=2`、SDK error 计数为零或一次可见截图单独视为显示器已接收生成帧。每帧全资源扫描、重复内容 hash、多套严格认证模式也不属于实现目标。

UI 分离属于 v1.0.0 的独立范围，不再作为 v0.8.0 的 P3/P4 验收项或阻塞条件。v0.8.0 仍需完成真实画面、运行时节奏和物理显示证据的验证；SDK errors 为 0、`actual_presents=2` 或单张截图都不能单独证明这些条件。

## 当前状态

### P0：共同时序契约与 Gate 1

共同时序契约和游戏侧接入基础已经存在。维护者于 2026-09-27 接受 Gate 1 **PASSED**，已知 SDK 同步例外转入 roadmap backlog，不再阻塞 Gate 1。官方 Streamline `v2.14.1` sample 在隔离修正 validation wrapper 后复现了与 LO probe 相同的 SDK clone 初始布局和 pacer semaphore 迹象；这些历史证据仍保留，不能将 validation 日志改写为零。

当前最精确的 SDK 证据是：clone image 以 `UNDEFINED` 初始状态出现，首次可见布局操作却使用旧 `TRANSFER_SRC`；另有 SDK 内部 shader write 与 transfer write 的访问范围冲突，以及 pacer semaphore 提前复用。现有外围 host fence 不能证明已修复这些 SDK 内部状态。run01/run02 已证明限定路径清理完整；更广生命周期覆盖、生成帧实际显示和外部显示证据仍待后续，validation 日志也保留其原始结果。

P0 的开发重点是补齐真实游戏路径的可归因证据：核对 `eBlockPresentingClientQueue` 下 post-present 队列提交与完成 fence、pending use 和 release 顺序，确保 resize、模式切换和退出时的资源生命周期正确。旧 `eBlockNoClientQueues` 诊断所需的 SDK fence/value 属于另一种同步模式，不能直接套到当前游戏路径。completion、设备或同步失败允许清楚报错并安全终止；当前没有证据支持把每类故障都平滑回退。现有 sample 复现可以复用为归因材料，无需为编写新文档再跑一次。

### P1：独立 FSR SR 基线

P1 原定义是 **FSR 可运行版本**，已完成有界验收，属于本阶段必须保持的基线，不应改写成 P3，也不应因 P4 继续开发而重开原 P1 验收。现有证据覆盖 Windows Vulkan、原生 Linux、Quality、Balanced、Performance、Native AA、受控运动下的 depth/MV 契约、提交、失败回退和 reset。P2 在 v0.7.0 已记录范围内也已验收；Steam Deck 实机、更广场景和 FG 不随之验收。

P1 的所有权不变：FSR 独立拥有其 SR 输入、输出尺寸、jitter/reset 和失败回退状态；DLSS 或 FG 接入不能覆盖或绕过这些语义。P4 只对直接受影响的组合路径补充验证，不重复宣称 P1 已验收范围。

### P4：Windows Vulkan 固定 2× DLSS FG

实验性 Windows Vulkan native DLSS SR+FG 游戏路径已接入，构建开关为 `LO_ENABLE_STREAMLINE_FG=ON`，运行时 `LO_DLSS_FG=1` 默认关闭。当前路径准备真实 color/depth/motion 输入，使用有限投影深度转换、`eBlockPresentingClientQueue`、post-present fence 检查和窗口 handshake；运行时 snapshot 已缩减为 depth+motion 两张纹理，`DepthRemapper` 资源在 checked SDK input drain 后复用，最终 resolve 在同一 submission queue 上按 serial 有序发布，session lease 保留到 checked SDK 完成。为保持FG尽可能连续，`Hybrid`可在同帧像素、抖动和reset合同满足时进入FG资格检查；几何运动优先，camera/depth用于补洞，动态对象未完全追踪仍需画质验证。原始SR的FG plan限制和P1所有权不变。

RTX 5080 的受控运行已证明限定场景可以正常退出，并观察到 generated intervals、presents、SDK errors 0 以及同场景 CPU/GPU overlap 改善。`run11-perf-focused` 记录 2,567 个 generated intervals、6,407 次 presents，SDK errors 0；这不等于 validation-clean、physical 120 FPS、完整画质覆盖或用户验收。AltEnter 尝试没有产生 AltEnter/resize 日志，窗口切换尚未验收。

## 实现任务

编号用于本文件后续证据引用，不代表已有 tracker 项目编号。

### P0 任务

- **P0-01 输入完成与 checked SDK 生命周期**：核对 FG 输入包从 snapshot、提交、post-present completion 到 lease 释放的路径，缺失证据时才补有界诊断。当前模式必须有成功提交并实际完成的队列 fence 才能复用输入；若改为显式 SDK completion 模式，则另行验证 SDK fence/value 契约。无法确定完成时保留资源并按错误路径处理；不得仅凭 `Hybrid` 标签判定合格或拒绝，必须检查同帧资源、相机和元数据，动态对象覆盖与画质另行验收。
- **P0-02 clone/layout 与 pacer 归因**：用同一版本的真实游戏路径和最小官方 sample 证据区分 SDK 内部初始布局/state cache、访问范围和 pacer 复用问题；不添加没有证据支持的 host 同步 workaround。
- **P0-03 resize、模式切换与退出**：验证 quiesce、局部首帧 reset、pending use 托管、未提交工作取消和已提交工作按 completion serial 回收。关闭双方 session 前完成资源释放，并把清理结果传递到最终退出状态；completion 失败可安全终止，不要求新增通用复杂状态机。
- **P0-04 Gate 1 证据包**：在修复证据稳定后，整理 executable 标识、完整日志、validation/SDK 计数、退出码、生成状态和显示侧材料。原始门槛仍作为工程标准保留；本轮维护者已接受 Gate 1 通过，已知 SDK 同步例外转入 backlog。

### P1 保护任务

- **P1-01 SR 所有权回归**：在 P4 组合路径变更后，确认 FSR 独立控制 SR 输入、输出尺寸、jitter/reset 和 fallback；使用已有 P1 验收作为基线，不扩大为 P2 画质或全游戏验收。
- **P1-02 尺寸与 Native AA 回归**：只覆盖受 P4 改动直接影响的低分辨率输出、原生尺寸、resize 和 reset 路径；输入临时不可用时回到当前帧渲染结果，其他错误按 `SrFailureAction` 处理。
- **P1-03 生命周期边界**：确认 FSR 资源、motion/depth 输入和 FG lease 不交叉释放，不因 FG 暂停、恢复或 provider 不可用而损坏 P1 的独立状态。

### P4 任务

- **P4-01 feature probe 与组合状态**：建立基于实际 probe 和输入状态的 DLSS Quality+FG、DLAA+FG、FSR+FG 开关；provider 不可用或输入不完整时停用 FG 并保留对应 SR/原生状态，同步或 completion 失败则按现有安全错误路径处理，不虚构平滑回退。
- **P4-02 固定 2× 生成节奏**：确认游戏逻辑、输入判定、音频和过场按原节奏推进，生成帧只影响呈现序列；记录 host presents、SDK reported frames 与实际显示证据的区别。
- **P4-03 生命周期场景**：覆盖暂停/恢复、切场景、电影、resize、最小化、窗口模式切换和退出。切场景、暂停和电影不按场景类型硬关FG；输入有效时保持开启，只有输入失效或resize等必要边界暂停，并自动恢复。记录实际enable占比、最长中断、原因、首帧reset、资源回收和baseline保存结果；当前仅Uhra路线的48个enabled周期样本证明了这一连续性目标，不要求把所有错误转成继续运行。
- **P4-04 画面与显示验收**：在至少一条真实游戏路线中核对 HUD 合成、边缘、运动稳定性和输出尺寸；补充实际显示器证据后，才能讨论显示端生成帧。
- **P4-05 性能记录**：保留 FG-off 同场景基线，并分开报告 frame time、renderer GPU time、fence wait、presents 和生成区间。限定场景的 overlap 改善不能泛化为全游戏收益。

## 接口不变量

1. **SR 所有权**：DLSS、FSR 和原生路径各自拥有明确的输入、输出尺寸、jitter/reset 与 fallback 状态；FG 不得隐式改变 FSR 的 SR 语义。`SrUseToken` 的 provider、device epoch、use id、request signature 和 geometry epoch 必须随 token 路由，不能用全局当前状态代替。
2. **输入契约**：depth 与 motion 必须来自同一真实场景帧，并匹配当前有限投影、尺寸和 temporal epoch；缺失或过期输入不得发布为可用 FG 输入。
3. **输出与提交顺序**：`composite` 的输出 region、最终 resolve 和 swapchain 尺寸必须匹配；窗口变化时清空旧 composite 并重新建立尺寸状态。final resolve 成功提交到目标 submission queue 后才写入 serial；present semaphore 的 GPU 顺序不能由 CPU 假设替代。
4. **资源生命周期**：已提交 lease、纹理、descriptor、framebuffer 和 session 资源保留到对应 provider/SDK completion serial；未提交工作可取消，已提交工作不能提前释放。
5. **同步边界**：SDK checked completion、producer fence、present fence 和资源复用各自记录，不能用 SDK error 计数为零替代 validation 或显示证据。
6. **状态切换**：只有输入或资源发生必要变化时才暂停 FG，完成必要 drain/reset，并允许下一帧按当前 probe 状态自动恢复；pause、切场景和电影在输入仍有效时保持启用。completion 或设备同步失败可以安全终止并保留资源，不宣称平滑恢复。
7. **测试运行方式**：不需要显示或窗口事件时使用后台、静音和隔离输出；需要显示、窗口切换或外部显示取证时才安排前台运行。后台运行没有生成帧不能单独判定 FG 失败。
8. **数据保护**：验证使用隔离的 shader cache 和复制的 settings/save/profile；测试结束要证明原始存档和设置保护结果，不能把实验输出写回用户数据。
9. **默认行为**：FG 默认关闭。实验性路径未达到验收门槛前，不改变普通构建的默认 SR、UI 或呈现行为。

P1 的失败动作遵循现有 `SrFailureAction` 语义：输入不可用才进入当前帧 fallback，需要重配置才重配置，不可用/失败才停用请求，设备丢失才停止设备。不得把所有错误统一记录为 fallback 继续运行。`PresentFrame::ProviderReady` 表示通用呈现合同资格；其返回 false 不否定实验性游戏路径已经产生生成区间。`ReadyForOrderedSubmission` 表示在既定队列和 semaphore 顺序下可继续提交，不要求 CPU 已等待 producer 完成；它也不证明 provider completion 或实际显示。

`TemporalFrameInputs::CompleteForConsumer` 的 SR路径仍保留原有FG plan和provider边界；FG资格检查可以接受同帧元数据完整的 `MotionState::Hybrid`。这不是SDK对Hybrid的禁止，而是项目必须验证像素级运动、抖动、reset和动态对象覆盖的输入合同。现有 Reflex markers 只覆盖 host presentation 事务，完整 guest 输入延迟测量另行取证。

## 开发顺序

1. 从现有游戏路径推进 P0-01～03，先补明确的同步和生命周期缺口；已有 sample、CPU 和 GPU fixture 结果继续复用。
2. 同步完成 P4-01 的组合能力判断及 FSR+FG 输入接线，按实际改动执行 P1-01～03，保留已经可用的 SR 基线。
3. 完成 P4-02～03 的节奏和状态切换，确认窗口事件真正触发。P3 只提供必要的资源交接依赖，不重新实施已存在的底座。
4. 补齐显示与画质材料，再形成 Gate 1 和 P4 验收结论。

这些是执行次序，不意味着所有本地开发必须等待 Gate 1 通过。只有完成声明和正式交付需要对应的验证与验收证据。

## 完成条件与证据入口

P0 的 V0–V2 同步和生命周期证据仍是工程验收标准；本轮维护者已接受 Gate 1 通过，并将已知 SDK `PRESENT-AFTER-WRITE` 例外转入 backlog。SDK sample 能复现问题或游戏退出码为零仍不能把 validation 日志改写为零，也不扩大显示、失败注入或设置重启覆盖范围。

P1 继续以既有有界验收为完成基线。P4 变更造成的直接回归只需执行 V3 覆盖的最小集合；若发现输入契约、fallback 或尺寸/reset 回归，再扩大范围并重新评估 P1 基线。

P4 只有在 V4–V8 覆盖三种组合、状态和生命周期场景、实际画面/节奏以及显示证据后，才可称为固定 2× DLSS FG 验收完成。生产路径在此之前继续保持 opt-in 和默认关闭。
