## 0. 结论

### 问题 1：主视角能不能靠 GMEM 变快？——不能，合并 pass 后也不能

- **强制 GMEM 后，主视角在每一种 pass 结构下都更慢**（原生分辨率，热态，单帧逐 pass 计时）：

  | 主视角 | sysmem（Turnip 现在的选择） | 强制 GMEM | 变化 |
  |---|---|---|---|
  | 现状，78 个 pass（Q08 → Q11） | 29.4 ms | 76.7 ms | +161% |
  | KEEP_COLOR=1 合并后，12 个 pass（Q07 → Q12） | 29.2 ms | 41.9 ms | +44% |
  | 同上，内部 1080（Q20/Q23 → Q22） | 16.3–17.8 ms | 30.7 ms | +75–90% |

- **大 pass 本身就输**：这几个 pass 一共只有 3 个，单个 pass 的载入和写回只占很小一部分，所以输的原因不在 load/store。
  - Z-prepass（1090 次操作，纯深度）：4.17 → 5.81 ms（×1.39）。
  - 主颜色 pass（620 个 draw）：7.72 → 10.06 ms（×1.30）。
  - 第二个颜色 pass（359 个 draw）：4.36 → 6.15 ms（×1.41）。
  - 在 1080 下更差，是 ×1.7–2.2。
- **GMEM 唯一赢的地方**是 KEEP_COLOR 合并出的那个光照 pass（71 个 draw，FP16 混合）：原生下 5.21 → 4.90 ms（−6%）。但在 1080 下它也输（2.52 → 3.17 ms）。
- **为什么输**：u_trace 显示，主视角的 FP16 + D32S8 附件在 2560x1636 下要分 22 个 bin（只有颜色时 14 个）。每个 bin 都要把落在里面的 draw 重放一遍，几千个 draw 乘以 22 个 bin，这部分开销比 GMEM 省下的带宽还多。分辨率降低时，省下的带宽随像素数变少，可重放的开销不变，所以 1080 下输得更多。
- **最理想的估算**（推导见 §2）：把主视角合成一个 pass，并假设除了一次之外所有的载入和写回都省掉，GMEM 下仍要约 33 ms，比 sysmem 的 29 ms 慢约 13%。如果按每个 pass 分别挑 sysmem 或 GMEM 中较快的那个，最多省约 0.3 ms，是主视角的 1%。
- **结论**：在 Adreno 750 + Turnip 上，合并 pass 不会因为能走 GMEM 而带来收益，更谈不上倍数级。主视角的 25–30 ms 是 sysmem 下真实的着色和带宽开销：FP16 颜色、D32S8 深度、约 2300 次操作。pass 的固定开销不是主因。

### 问题 2：KEEP_COLOR 在 Adreno 上为什么慢 9%？——平板上复现不出来，平板上它基本持平

- **平板（Adreno 750，Turnip 26.0.0）上 KEEP_COLOR=1 不慢**。最可靠的是两组 ABBA，排在表的前两行：

  | 对照（都是热态 status 3） | KEEP_COLOR=0 FPS | KEEP_COLOR=1 FPS | 差 |
  |---|---|---|---|
  | 强制 sysmem，原生，ABBA（Q05/Q08 vs Q06/Q07） | 20.8、20.2 | 20.6、20.5 | +0.2% |
  | autotune，内部 1080，ABBA（Q19/Q24 vs Q20/Q23） | 26.4、26.0 | 26.4、26.0 | 0% |
  | sysmem + nolrz，原生（Q09/Q10，相邻两次） | 20.1 | 20.3 | +1% |
  | autotune，原生（Q04 vs Q02/Q03） | 20.9 | 22.0、21.6 | +3–5%。但 K1 的两次排在前面，机身 50–51 °C，Q04 是 52 °C，这一段升温最快，所以不能把这个差值都算成 K1 的收益 |

- **pass 数确实少了**：每帧从约 308 降到约 248。主视角从 78 个降到 12 个：Z-prepass 带上了颜色附件；约 67 个交替 pass 合成 5 个，其中一个是 71 个 draw 的光照 pass。
- **主视角 GPU 时间**按未受影响的 pass 归一后：
  - sysmem 的 ABBA 组里 ±0；
  - autotune 下 −8%，但这组是 Q03 对 Q04，中间隔着一次 1 °C 的升温，而且只有单帧，可信度比 sysmem 组低；
  - 两者都在单帧计时的噪声以内（±6%）。
- **两个假设都不成立**：
  - 假设 1（autotune 改选 GMEM）：u_trace 显示，KEEP_COLOR=0 和 1 下 autotune 都给 **100% 的 pass 选了 sysmem**（Q16、Q17、Qsmoke）。
  - 假设 2（纯深度 framebuffer 在 sysmem 下有更快的路径，例如 LRZ）：强制 sysmem 和 nolrz 下 K1 也都不慢；而且整帧关掉 LRZ 本身只差约 0.5%（Q08 20.2 vs Q09 20.1）。
  - 注意：`nolrz` 是否真的生效，只确认到 `TU_DEBUG=sysmem,nolrz` 这个字符串到达了驱动（日志的 `diag env` 行）。同一路径传的 `gmem` 和 `perf` 都看得到效果，但这两次没有用 u_trace 核对 `lrz` 字段。
- **手机上那 −9% 最可能的来源**（推测，没有在手机上验证）：
  - 手机用的是 PurpleVK（Mesa 26.3-devel），upstream 2026 年改过 autotune（`TU_AUTOTUNE_ALGO`）。
  - 平板实测，K1 后带颜色附件的 Z-prepass 一旦走 GMEM 就慢 2.8 倍（3.6 → 10.1 ms，+6.5 ms）。
  - 如果 PurpleVK 把这个 pass，或者合并后的其他大 pass 判成了 GMEM，正好会慢 9–15%。
  - 另一个可能：据 2026-10-07 的记录，手机那次实验在 PR #313/#315 之前。这两个 PR 让纯深度 pass 快了约 20%，改变了两种结构之间的相对成本。
  - 也可能是 Adreno 840（a8xx）硬件本身的差异，平板上测不到。
- **建议在手机上补一次**（需要维护者同意）：KEEP_COLOR=0/1 各配 `LO_TU_DEBUG=sysmem`，再跑一次 u_trace（本次的 `LO_ENV_MESA_GPU_TRACES`）看 K1 下每个 pass 的 `tiledRender`。如果强制 sysmem 后 −9% 消失，就是 autotune 的问题。

### CPU：每类 pass 的录制开销（渲染线程，原生，K0，14 帧中位数）

- 一帧录制总共约 35 ms（含 trace 本身的开销；同期 `draw_ms` 中位数 29–31 ms）。内部 1080 下几乎一样（34 ms），说明这部分和分辨率无关。
- 按类别：

  | 类别 | pass 数 | CPU ms/帧 | 说明 |
  |---|---|---|---|
  | 主视角大 pass（Z-prepass + 两个颜色 pass，约 2070 次操作） | 3 | 23.9 | 每个 draw 8–15 µs，是录制的主体 |
  | 主视角交替 pass | 72 | 3.6 | 每个 pass 30–70 µs |
  | 阴影/离屏深度 | 57 | 2.4 | |
  | **A 类 EDRAM 别名清除** | **139** | **2.2** | 每个 pass 约 16 µs。其中 A2（深度别名清除）1.44 ms，A1 0.41 ms，A3 0.18 ms |
  | 主视角纯颜色 pass | 4 | 0.95 | |
  | present | 1 | 0.5 | |
  | 小 RT、transfer、resolve blit | 27 | 1.1 | |

- **每个 pass 的边界成本**：KEEP_COLOR 少掉 60 个 pass，trace 测得的 CPU 从 35.4 降到 34.9 ms，即每个 pass 约 8–10 µs。这是本报告采用的数字。
  - A 类每个 pass 约 16 µs 更高，因为里面还包含别名遍历、`MapDepthClear` 和矩形合并这些渲染器逻辑。
  - `draw_ms` 也低了约 0.5–1 ms，方向一致。但 K1 的几次排在前面、更凉，这个差值和热漂移在同一量级，只作旁证。
- 注意：pass 是在第一个 draw 时才开始的，所以每个 pass 的"内部"时间里也算进了下一个 pass 第一个 draw 的准备工作。按类别加总时，这部分会往前错一个 pass。对 A 类和交替 pass 的估计影响在 ±30% 以内，对总量没有影响。

### LRZ 每帧基线（`TU_DEBUG=perf`，Q15，原生，K0，窗口内 433 帧）

| 原因 | 每帧次数 |
|---|---|
| `CmdClearAttachments`（关掉整个 pass 的 LRZ） | 72.8 |
| `stencil write based on depth test`（本 pass 余下部分不写 LRZ） | 43.8 |
| `FS writes depth or has side-effects` | 34.8 |
| `Depth write + ALWAYS/NOT_EQUAL` | 22.5 |
| `Stencil may kill fragments` | 2.0 |

- 与同一天的 P3（普通 APK）在窗口内重新统计的结果一致：72.9 / 44.0 / 34.9 / 22.6 / 2.0。Q15 用的是诊断 APK，但两边的数字相同，说明这些次数不受诊断补丁影响。
- 但 **LRZ 对整帧的价值很小**：sysmem 下整帧关掉 LRZ（`nolrz`，Q08 20.2 → Q09 20.1 FPS，相邻两次）只差约 0.5%，在漂移范围内。主视角有 Z-prepass，颜色 pass 靠 early-Z 已经够了。所以阶段 1 消掉 `CmdClearAttachments` 带来的 LRZ 收益可以忽略。

### 其他开关

- `LO_VK_NO_END_DEP=1`（Q13）：19.9 FPS，夹板 Q14 也是 19.9；主视角/其余的比值是 1.98 对 1.96。**没有可测的差别。**
- `TU_AUTOTUNE_ALGO`：在 Turnip 26.0 里**不存在**。26.0 的 `tu_debug_options` 表里没有，驱动二进制里也找不到 `prefer_sysmem`/`prefer_gmem` 字符串。
- 和本问题有关的 26.0 开关（来源：`src/freedreno/vulkan/tu_util.cc`，26.0 分支，取自 GitHub 镜像 `AHMETBAYIR/mesa-mirror`，并与驱动 `vulkan.ad07xx.so` 中的字符串核对）：`sysmem`、`gmem`、`nolrz`、`nolrzfc`、`nobin`、`forcebin`、`nobinmerging`、`perf`、`log_skip_gmem_ops`、`nocb`/`forcecb`（并发 binning）。本次选用了 `nolrz`。
- 以后做 A/B 可以用 `TU_DEBUG_FILE`：它支持运行时切换 `sysmem/gmem/nolrz/perf` 等标志，不用重启进程（代码见 `tu_runtime_debug_flags`）。

### 建议

- **阶段 1（清除延迟执行 + loadOp=CLEAR）：照做，但要把预期调低，而且理由要改。**
  - 不靠 GMEM 和 LRZ：autotune 本来就全选 sysmem，LRZ 也几乎不值钱。
  - 实际可省的：
    - GPU：原生热态下 A 类 2.3–3.0 ms，占 pass 时间的 6–7%。其中只有不再需要执行的那部分能省。
    - CPU：渲染线程上 A 类约 2.2 ms，占 6%。
  - 原生（GPU 受限）下预计最多快约 5%。
  - 720p/1080 这类接近渲染线程上限的设置下，CPU 那部分更有用：1080 热态 `draw_ms` 30 ms，比 GPU 的 27–28 ms 还长。
  - Apple 上的收益另外测。
- **阶段 1b**：阴影段的 pass 数会下降，但阴影段 GPU 总共只有约 1 ms，GPU 收益很小。CPU 上阴影段是 2.4 ms，这是做它的主要理由。
- **阶段 2a（主视角交替合并）：在 Adreno 上不建议开。**
  - 平板上持平，GMEM 也帮不上忙。
  - 手机上还可能因为驱动的 autotune 变慢。
  - 保持 Apple 默认开、Android 默认关。等手机补测（见问题 2）之后再决定。
- **阶段 2b（transfer 画进目标 pass）**：G 类 3.3 ms，但 transfer 本身仍要画，sysmem 下省的只是 pass 边界，预计 <0.5 ms（估计），优先级低。"常量 transfer"（§2.4 设计）能省掉 transfer 本身，这一部分仍值得在阶段 1 里先计数。
- **阶段 3（按 Turnip 调 GMEM、storeOp、pass 内 resolve）：建议放弃。**
  - 主视角即使合并、即使省掉 load/store，GMEM 仍然不如 sysmem。
  - 唯一赢的光照 pass 只省 0.3 ms。
- **API 级重写：不值得为合并 pass 去做。**
  - 这次的数据说明，pass 结构不是 Adreno 上的瓶颈：
    - sysmem 下，pass 边界、尾部依赖和 LRZ 加起来都在噪声以内；
    - GMEM 在这个场景下整体是输的。
  - 要得到倍数级的提升，只能从两头下手：
    - 每像素的 GPU 成本：FP16 的 8 字节每像素宿主格式、着色。但改格式就不能保证逐字节一致。降分辨率维护者不接受。
    - 每个 draw 的 CPU 录制成本：每个 draw 8–15 µs，乘以 2300 个 draw，约 25 ms。
  - 如果以后考虑重写，目标应该是每个 draw 的 CPU 成本和每像素的 GPU 成本，而不是 render pass 的组织方式。

## 2. 推导：主视角合并到个位数 pass 并走 GMEM 能省多少

把 KEEP_COLOR=1 的主视角（12 个 pass，Q07 sysmem 29.2 ms，Q12 GMEM 41.9 ms，两次热状态相近，机身 53–54 °C）当作"合并后"的近似，分三步估计：

1. **按 pass 择优**：每个 pass 取 sysmem 和 GMEM 中较快的。只有光照 pass 选 GMEM，省 5.21 − 4.90 = **0.31 ms**（主视角的 1%）。
2. **假设 load/store 全部省掉**（这是乐观的上限，现实做不到，因为 resolve 要求写回）：
   - 单 draw 的 GMEM 颜色+深度 pass 一共 0.875 ms，可以近似看成一次完整的载入加写回，约 0.8 ms。
   - 这个 pass 里还包含 binning 和 22 个 bin 各重放一个 draw 的开销，所以 0.8 ms 只是载入加写回的上限。按它扣得多了，下面的 33 ms 是合并后 GMEM 成本的**下限**，结论偏保守。
   - 12 个 pass 里去掉 11 次：41.9 − 11 × 0.8 ≈ **33 ms**，仍然比 sysmem 的 29.2 ms 慢约 13%。
   - 在 1080 下，按像素数缩放成每次约 0.45 ms：30.7 − 11 × 0.45 ≈ 25.7 ms，而 sysmem 是 16.3–17.8 ms，慢约 50%。
3. **为什么省不下来**：
   - 剩下的主要是每个 bin 的重放成本。Q18 的 u_trace 里，K1 的 Z-prepass 在 GMEM 下有 22 个 bin，整个 pass 8.15 ms，其中 FP16 载入约 0.8 ms，余下约 7.3 ms 是逐 bin 执行 draw，而 sysmem 一共才 3.6 ms。
   - 这部分和 pass 怎么切无关，只取决于 draw 数和 bin 数。bin 数又由附件格式决定：FP16 + D32S8 是 12–13 字节每像素。

**不确定性**：

- 单帧 trace 的 GPU 时间有 ±10–15% 的噪声。
- 载入加写回按 0.8 ms 估算，是从单 draw pass 反推的，没有直接测到（写回是异步的，u_trace 的时间戳看不到）。
- 强制 GMEM 时，驱动对所有 pass 都用 GMEM，包括它自己判断不该用的那些。这只影响非主视角部分，主视角的比较不受影响。
- 只测了 Uhra 一个场景。几何更少、混合更多的场景，GMEM 的相对表现会好一些。

不过 GMEM 在三个大 pass 上都输了 15–40%，在 1080 下输了 70–180%，这个量级远远超过上面这些不确定性。

## 3. 方法和限制

- **诊断补丁**：`apply_diag_q.py`，在 `apply_diag_v100.py` 的基础上加了以下内容。用 `restore_diag_q.py` 还原。
  - 每个 pass 的 CPU 时间：`steady_clock`，在 `vkCmdBeginRenderPass` 前和 `vkCmdEndRenderPass` 后各取一次。记两段：pass 内部，以及从上一个 pass 结束到本 pass 开始。帧边界那一段（present 到下一帧第一个 pass）单独列出，不计入类别。
  - AO、present、TAA 的站点标记，分别加偏移 100000、200000、300000。renderer.cpp 的站点号和 D1/D2 相同。
  - 用命令文件 `LO_DIAG_CMD_FILE` 触发 trace，在 20 s 窗口结束之后再录，不会污染计时窗口。
  - `LO_ENV_*` 转发，用来传 `MESA_GPU_TRACES`、`TU_GPU_TRACEPOINT` 等。
  - 启动时打印一行开关状态，用来核对 KEEP_COLOR 和 NO_END_DEP 是否生效。每次运行的日志里都有 `diag env:` 这一行。
- **APK 的一个缺陷**：同一次运行里第二帧及之后的 trace 复用了同一个 query pool，读到的是旧的 GPU 时间戳。所以 GPU 数据只用 trace n=0；CPU 数据每一帧都有效。脚本里已经改成每次 trace 换一个新的 pool，并编译通过，但没有重新跑设备验证。
- **logcat 偶尔丢行**：一次性写出 300 行时，logd 偶尔会丢掉一部分，所以分析脚本优先读拉回来的 runtime 日志。
- **单帧 trace 偶尔有帧边界空闲**：present 之后到下一帧第一个 pass 之间，GPU 有时空闲 1.5–12.5 ms，不同运行之间不一样，和 KEEP_COLOR 无关。已从类别统计中排除，没有进一步查。
- **热态**：维护者要求不单独热机，第一次运行（Q01，冷机）的数值明显偏高，只作参考。其余各次都在 status 3，机身 50–55 °C。
