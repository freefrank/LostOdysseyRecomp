# v0.7.0：DLSS-G 与 FSR FG 开发计划

规划日期：2026-09-13。用户明确指定交付目标 **v0.7.0**，覆盖 **D3D12 和 Vulkan**。本次完成开发规划；运行时实现、性能验证、玩家验收与发布均待后续开发任务完成。源码版本号不因记录计划而修改，也未指定发布日期。

## 交付范围

v0.7.0 的基础交付为 Windows PC 上两种 API、两种插帧提供方的 **2× 模式**，即每个正常间隔生成一帧。四个组合独立验收，一个组合通过不能代替其他组合。D3D12 先用于定位输入问题，Vulkan 从设备／队列设计阶段同步推进，不能留到发布前才移植。

| 提供方 | D3D12 | Vulkan | 基础交付要求 |
|---|---|---|---|
| NVIDIA DLSS-G | 必须验收 | 必须验收 | 查询实际硬件、驱动、系统和 SDK 能力；先完成 2× |
| AMD FSR FG | 必须验收 | 必须验收 | 使用验证过的跨厂商解析式 FSR 3.1 FG 路径；支持范围按实测设备记录 |

FG 与超分／AA 设置分开：现有 AA 和空间缩放可以继续作为真实帧生产者；启用 FG 不要求先完成 DLSS SR、FSR SR。更高插帧倍率、FSR ML FG、DLSS-NR、Ray Reconstruction、DX11、Switch 和 Linux/Steam Deck 不作为本计划的基础验收项。Vulkan 是必需的图形 API，不能由此推定另一个操作系统已经通过验收。

## 当前基础与必须先验证的假设

已有 scene/depth 选择、相机重投影、32 相位 Halton jitter、历史重置、shader 翻译和有界反馈采集。当前稀疏包采样 GPU 深度，再用前后相机推算 MV；它不能证明角色、骨骼和粒子运动完整。此前 TAA 场景通过记录仅在原证据范围内复用。

当前 host 没有已建立的稳定物体实例身份及前帧 GPU 骨骼 palette。shader hash、draw ordinal、vertex-buffer 地址都不能单独充当物体 ID。现有 `PositionVPSlot` 是相机常量识别表，不是骨骼或 world-matrix 语义表。

但保留的 2026-09-10 本地提交研究（`out/save-temporal-survey-20260910/submission-research.md`，未纳入公开仓库）已发现 **原生 velocity 路径**。优先研究能否复用它，不能直接假定游戏完全没有运动输出，再从零重放所有几何：

| 路径 | 历史静态线索 | 尚需证明 |
|---|---|---|
| Native velocity | `0x8274C318` / `0x8274C8A0` shader 构造；`0x8274CEA8` eligibility；`0x8274CCB8` 上传 current/previous local-to-world | 当前版本与场景是否执行、RT 与编码、清除值、完整覆盖及失效条件 |
| Skeletal submit | `0x823CB350` / `0x823C87D8`；proxy、section、material 与 draw record | 对象生命周期、同一 GPU draw 关联、稳定 generation |
| Bone source | 已知局部 atoms 和相对常量访问 shader | component-space 合成、inverse bind、section BoneMap、最终 palette 上传及前帧副本 |
| Camera history | `0x8274C478` 的命名 current/previous VP 上传 | 当前 build/input 身份、同一渲染帧、reset/cut 与实际 raster 对应 |

上述地址来自保留的亚洲版 PPC 研究，不是本次新运行结果；重新使用前先核对输入和编译身份，其他版本不能直接套用地址。原生 velocity 即使存在，也可能仅覆盖 motion-blur eligible objects 或使用特殊缩放／clamp。

## SDK 和 API 路线

NVIDIA 基线选用 [Streamline 2.14.1 DLSS-G 指南](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.1/docs/ProgrammingGuideDLSS_G.md) 对应的版本，提供 D3D12/Vulkan 集成路径，要求 coherent frame inputs、正确资源寿命、帧标识和 Streamline Reflex。P0 固定实际 SDK commit、签名插件版本及哈希，检查 application ID、再分发要求和能力查询结果；不能仅固定指南版本。Dynamic MFG 和 FG VSync 不作为双 API 通用承诺，依照该版本的平台支持分别暴露。

FSR 基线采用 **FidelityFX SDK 1.1.4 / FSR 3.1.4 FG**，分别验证 D3D12 与 Vulkan 接口／swapchain，使用同一算法版本减少差异。官方 [v1.1.4 发布](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/releases/tag/v1.1.4) 对应 commit `c6efa6bf7f2027b3ec94f28578bb5965eabb9e55`；[固定版本集成文档](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/v1.1.4/docs/techniques/super-resolution-interpolation.md)保留 Vulkan 路径。P0 锁定下载包、许可证、哈希和所需补丁；源码许可与供应商预编译件分发条款分别检查。

较新的 [AMD FSR SDK 2.3](https://gpuopen.com/amd-fsr-sdk/)页面列出的交付 API 是 DX12，包含 FSR FG 3.1.6、ML FG 4.0.1 与 swapchain 3.1.7。它作为后续更新候选，不能被用来推断 Vulkan 已具备同等支持，也不能悄悄把本次 FSR 范围收缩为 Radeon 特定硬件。若旧版有阻断问题，先评估有来源的定向修复或另一已验证版本，再更新版本决策。

## 共用运行时接口

renderer 与 presentation 之间已有受限的 producer snapshot 试验：成功的 SR scene recording 可在 `LO_FG_SNAPSHOT_FRAME=N` 指定一次真实帧，复制 source color/depth/motion/invalidity/SR-scene candidate 五类 GPU texture，并在 producer fence 前保留副本。该选项默认关闭，metadata 会清除借用的 optional views；失败 submit 丢弃 packet，失败 wait 保留 pending。当前 packet 仅用于诊断，`UI=Unavailable`，没有 provider 或 final resolve 关联，也不证明生产级 HUDless/UI 分离、真实 UI handoff 或可发布的 `FrameGenerationInputs`。数据留在玩家 GPU；上传统计不参与实时插帧。

| 字段组 | 必须明确的约定 |
|---|---|
| 身份与时间 | 真实渲染 frame ID、history epoch、单调时间、真实帧间隔；生成帧不推进游戏逻辑和对象历史 |
| 颜色 | 完成后处理、显示尺寸一致的 HUD-less color，最终 backbuffer，颜色空间／HDR 元数据；早期 pre-UI resolve 不自动满足最终 FG 输入 |
| 深度 | 当前可见场景的完整深度、有效区域、格式、反向深度、相机 near/far 与投影语义 |
| MV | 完整 texture、有效尺寸、方向、单位、相机是否已包含、jitter 是否已包含、dilation 状态及来源覆盖 |
| 相机与 jitter | 无 jitter 的前后矩阵、实际 raster jitter、分辨率与 viewport；CPU 原始矩阵和修改后 raster 常量分开 |
| UI | SDK 对应的 UI alpha／color 资源或可安全重放的 HUD callback；不从最终画面简单相减猜 alpha |
| 生命周期 | native resource、resource state/layout、生产 queue、fence/timeline 值、消费完成和回收时点 |
| 重置 | 首帧、切镜头、瞬移、加载、尺寸／显示模式变化、设备重建与 provider 切换 |

内部建议采用 current-to-previous、渲染像素／真实帧、不含 jitter 的 MV。供应商适配层分别换算单位和标志，并用已知平移验证符号。Streamline 和 FSR 的 scale 字段不能机械复制；[Streamline common constants](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuide.md) 与固定 FSR 版本的头文件分别作为依据。

每次只允许一个 FG 提供方拥有呈现包装层。UI 的 `Off / DLSS Frame Generation / FSR Frame Generation` 独立于 AA／超分；不支持时说明具体原因。初版优先保存独立 UI texture，与 HUD-less color 一起合成，避免从异步呈现线程重新调用 guest 游戏/UI逻辑；UI自身更新频率单独记录。关闭或失败时恢复正常真实帧呈现，不丢失设置、存档或可用渲染基线。

## MV 实现的具体规则

先查原生 velocity 输出能否按 SDK 约定解码／补全。若不可复用，则用稠密 camera MV 初始化静态背景，再为验证过的动态几何生成 velocity。渲染目标初选 RG16F，按误差和供应商格式支持验证。

动态几何的概念计算如下，实际乘法顺序服从项目的矩阵表示：

```text
currentClip  = currentCamera  × currentWorld  × deform(currentPose, vertex)
previousClip = previousCamera × previousWorld × deform(previousPose, sameVertex)
motionPixels = previousScreenPosition - currentScreenPosition
```

位置按同一表面点计算，在当前帧可见几何上栅格化；透视除法、插值与 viewport/W/half-pixel 转换必须一致。velocity pass 复用或复现原 draw 的深度、cull、scissor、alpha discard 和 deformation；不能将遮挡后的几何写入前景 MV。复用原生 pass 也需要相同验证。

对象历史初选 `instance + generation + mesh section + topology/deformation identity`。generation 必须来自已验证生命周期，不是将指针简单递增包装。骨骼优先保存真正提交 GPU 的 palette；仅有局部 atoms 不能直接替代。动态 VB、morph、布料等保留所需前帧数据或明确未覆盖。

以一次真实场景渲染为提交边界，depth/material/shadow 多次 draw 共享同一前帧快照。生成帧不推进快照。多帧在途采用带 fence 的环形持有，容量按实际 inflight 与 SDK 消费证明确定，不能强行复用现有两槽。对象重建、LOD/拓扑切换、瞬移、首次出现和不连续摄像机分别记录历史有效性；局部历史失效遵循 provider 契约，不能随意向纹理填 NaN。

透明物体、粒子、头发、反射和动画材质单独记录覆盖。存在光流结果可以辅助插帧，但不作为原生几何 MV 正确的证明。

## D3D12 与 Vulkan 的独立工作

D3D12 要确定设备创建／swapchain 包装顺序、native queue 归属、fence 依赖和 SDK 的 UI 回调线程。FG 开关／提供方切换采用明确状态机，先停止新任务、等待消费、销毁旧包装层，再恢复或创建目标；禁止 DLSS 与 FSR 同时包裹同一个 swapchain。

Vulkan 在创建设备之前确定队列数量、queue-family 能力和扩展。[v1.1.4 的队列契约](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/v1.1.4/sdk/include/FidelityFX/host/backends/vk/ffx_vk.h)要求 game queue 支持 graphics/compute、present queue 支持呈现且不被引擎并发使用；async compute 可选，image-acquire queue 推荐专用但允许有条件共享。不能把“四个队列角色”写成所有设备必需四个不同队列，也不能忽略 present queue 的独占要求。按实际 SDK允许的布局验证跨 family ownership、image layouts、内部semaphore/timeline与WSI acquire/present同步、resize失败恢复。Streamline 的 Vulkan hook 路径另行验证，不把 D3D12 的 DXGI 处理原样套用。

P0 对低队列数硬件建立能力矩阵；若 SDK 允许安全回退才能提供相应路径。出现队列／SDK阻断时，该硬件组合记录未支持；若影响计划必需的 API 交付，保留 v0.7.0 未完成状态并重新评估方案，不自行将 Vulkan 延后。

有针对性的合成数学／资源生命周期测试适合自动化；真实游戏只执行受影响场景。已通过检查在提交、换目录、打包阶段复用，不重复构建／重跑。自动测试后台运行、测试专用静音；依赖可见交互的试验另安排用户操作，不抢占前台。

## 256 KiB 诊断包：辅助交付，不是运行时输入

保留32帧稀疏记录及小型统计，在现有256KiB单请求限制内建立统一capture/frame关联。候选预算为头部4KiB、帧统计8KiB、现有稀疏包151KiB、3帧输入/输出96×54 R8亮度概览31KiB、4个32×32 R16F亮度ROI跨3帧输入/输出48KiB，总计242KiB，留14KiB余量。它是尚未实现的格式提案，须在实际编码后验证硬上限。

包内注明MV来源、采样率、坐标/单位、jitter应用结果和GPU完成状态；有限数值不等于正确MV，稀疏有效率不等于全屏覆盖。前后图需本地有界缓存；亮度ROI优先保留原像素，缺失或压缩/裁剪必须记录。客户端与Worker同步升级schema，检查同意状态、频率、日字节预算和失败退避，不能按256KiB无限连续上传。D1记录小包与关联；完整调试资源保留本地或另行按需提交。

基础MV验证不等待玩家图片上传；先用本机受控场景完成。更丰富遥测只是远程回归的辅助条件，不能用“没有上传数据”替代实现验收。

后续开始实现时先完成 **P0 的四组合能力表与 P1 的原生 velocity 实际命中证据**，再决定复用范围和补画路径。不要直接大范围双执行所有VS或拷贝全部常量／顶点历史。

跟踪复用现有 [Project #3](https://github.com/users/freefrank/projects/3) 中 `frame-generation-research`，依赖 `native-object-motion` 和 `temporal-color-exposure`。关联 [Issue #10](https://github.com/freefrank/LostOdysseyRecomp/issues/10) 的 FSR FG 需求，保留其超分／锐化请求独立状态，不创建重复 Issue。实现、每组合验证、玩家验收和v0.7.0发布分别记录。
