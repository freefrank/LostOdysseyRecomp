# 改进建议：v0.6.7 之后的渲染与设置界面

日期：2026-09-22。审计终点：`83655ac29d5aba85adc575c77ddf3269c8f40b6c`。配套的[bug report](post-v0.6.7-bug-report.zh-CN.md) 记录已确认缺陷；本篇给出后续实现建议，**在原审计时点均未实施**。当前状态：建议顺序第 1 项为**部分完成**（BR-01 帧生命周期与 BR-02 能力快照已修复并验证，BR-03 仅完成 CPU 计划反馈；motion pending、颜色编码未知、feature 重建等非闭锁暂态回退尚无实际执行快照与具体原因，BR-03 执行层状态反馈待补）；第 2 项（稳定行 ID 替代菜单与测试数字下标）及后续其余建议均仍待做，不视为已完成。

优先做能让玩家看懂、能避免再次写错、且适合个人维护的改动。继续使用现有 C++/SDL、软件 UI 和翻译表；不需要引入网页界面、通用插件框架或大规模安全认证流程。

## 一、设置先显示实际状态

当前配置表示玩家的请求，实际运行可能因为后端、NGX、尺寸查询或单帧 motion pipeline 尚未就绪而回退。建议在图形页增加一行简短的只读状态，例如：

- `DLSS Quality 已启用 · 输入 1707×960 → 输出 2560×1440`。
- `DLAA 已启用 · 2560×1440`。
- `DLSS 待启用 · 请切换 Vulkan 并重启`。
- `DLSS 暂时回退 · 正在准备运动数据`。
- `DLSS 不可用 · 当前设备未通过能力检测`。

这些是拟定文案，并非本轮测得的状态。状态来自 BR-02 修复后的线程安全值快照，不让 UI 访问 NGX 可变报告；可以复用现有 fallback/failure 分类，不再建立平行的判断规则。

“保存成功”继续准确表示配置写盘，同时显示当前实际效果。对需要重启的改动给出明确提示；不要用保存成功替代功能生效。设备不可用时可以保存未来要用的偏好，但应说明条件。暂态 pipeline pending 不应被展示为永久设备不支持。

## 二、理顺图形选项

### 将 DLAA 与 SR 质量档的意义说清楚

目前 DLAA 放在“DLSS quality”的第四格，技术上能共用实现，玩家却容易把它当成更高一档超分。可以先改帮助文案；如重排页面，可采用以下表达：

| 图像处理 | 相关选项 | 说明 |
| --- | --- | --- |
| 原生 | 传统抗锯齿：关 / FXAA / SMAA / TAA | 使用现有原生/legacy 分辨率规则 |
| DLSS 超分辨率 | 质量 / 平衡 / 性能 | 以较低输入分辨率重建输出 |
| DLAA | 无 SR 质量子选项 | 输入与输出内容尺寸相同，用于抗锯齿 |

这是界面映射建议，不要求迁移现有 `upscaler` 和 `dlss_quality` 配置编号。保留历史配置兼容，只在界面解释和显隐上改变。

DLSS 生效时，传统 AA 应弱化或隐藏，并说明由 DLSS 负责抗锯齿；避免玩家以为还能额外叠加 TAA。“缩放质量”与“DLSS 质量”现在容易混淆，建议将前者改成“普通缩放滤镜”，并说明它何时用于关闭 DLSS 或回退路径。

### 给遗留内部分辨率一个可见出口

内部分辨率行是本次明确移除的产品选择，不作为新 bug。但 `internal_resolution` 仍影响 legacy/fallback，历史值可能是固定 2160p；玩家在当前界面已经无法看到或修改它。

建议在高级区域保留“原生/回退内部分辨率：自动（当前值……）”，或至少提供“恢复自动”操作。不要在加载旧配置时无提示地覆盖用户选择。DLSS 实际生效时可收起该项，回退时让状态解释当前使用的尺寸。

## 三、设置界面的视觉与交互

### 视觉依据

本轮查看了 `out/snapshots/menu_1280x720.png` 与 `menu_1280x720_21_9.png`。两者是 **2026-09-20 的 v0.6.7 基线**，可以用于判断既有灰银色、箭头、像素字体和双栏结构，不能证明 v0.6.11 的 DLSS/滚动布局已经通过实图验收。新布局的判断来自当前源码。

基线已经有清晰的“左标签、右选项”结构，适合手柄。主要视觉问题是整屏灰色底纹和大量文字描边同时争夺注意力，十行图形选项显得密集，焦点箭头、已选值与可操作区域的层级还可以更清楚。

### 保留现有风格，先改四处

1. **降低背景噪声。** 减弱扫描线/纹理的对比，让内容区的灰阶更平稳。保留银灰与箭头语言，不必换成完全不同的现代卡片界面。
2. **区分焦点与选中值。** 焦点行用连续、轻量的背景带连接标签和选项；已选值使用稳定的浅色块；disabled 用较低对比并显示原因。避免仅靠细描边或颜色差异表达状态。
3. **统一文字层级。** 标签、值、辅助说明分别使用固定字号/行高。降低正文重复黑白外描边的强度，分辨率与帧率数字统一对齐；“实验性”可移到行旁短标记或帮助区，避免每格都塞长后缀。字体改动需保留现有中、日、韩覆盖，先试一个页面再决定。
4. **固定操作区。** 页面底部保留状态/帮助与“应用并保存、返回”，让保存动作不依赖滚到最后一行。修改尚未保存时显示简短标记；需要重启时放在同一区域。

如果决定重排，可将“显示”和“画质”作为图形页内两个分组，先降低一次出现的选项数量。下面只是结构草案：

```text
图形设置                           当前：Vulkan · DLSS Quality 已启用
显示 / 画质

输出分辨率          2560 × 1440
显示模式            无边框全屏
宽屏                关闭
帧率                60 FPS

当前项说明：更改输出尺寸后，重建模式会重新查询输入尺寸。
未保存的改动                        [应用并保存]  [返回]
A / Z 确认      B / Esc 返回      LB / RB 切分类
```

状态区不要显示 shader hash、NGX 返回码、epoch 等实现细节。需要排查时再进入现有日志/捕获功能。

### 键盘、手柄和鼠标要遵守相同逻辑

当前 [Start/Enter](../../LostOdysseyRecomp/settings/menu.cpp#L676) 只把焦点移到保存行，并抑制同帧确认；按第二次 Enter 也不会保存，因为键盘 Enter 映射 Start。近期最小改动是把真实按键提示补到帮助栏：`Start/Enter 跳到保存，A/Z 确认`。若希望 Enter 兼作确认，应明确规定“已经聚焦保存行时确认”，同时保留首按只定位的保护。

右侧选项看起来是独立格子，但现有鼠标处理对选择行主要执行“下一项”，不一定直接选择点中的格子。这是既有交互问题，新增四格 DLSS 模式后更容易造成误会。建议命中检测返回具体 option index，点击某格就选某格；手柄仍按左右循环。

长列表保留滚动指示，并让 hover、点击和手柄焦点共享同一套“可见行 → 逻辑行”映射。回归应覆盖隐藏质量行、打开质量行、滚动位置非零、点击首尾可见行；不要只验证默认第一页。

## 四、先做小型结构重构

### 菜单用稳定的行 ID

Graphics 页的 `Publish`、帮助、隐藏判定、动作判定、增减值、保存/亮度处理和测试重复使用数字行号。新增 Upscaler 和 DLSS quality 后，测试已经出现漂移：[menu_flow_test.cpp:481–489](../../tools/tests/menu_flow_test.cpp#L481) 仍用 `{5, 7}` 生成 `graphics-aa.bmp` / `graphics-rate.bmp`，当前它们实际对应 Upscaler / 普通缩放质量；AA 和 Frame rate 已在 4、8。

先引入 `enum class GraphicsRow`，集中定义 `Count`、显隐、可操作性和帮助映射，把测试也改成引用 ID。需要进一步减少重复时，再使用小型 row descriptor。无需为了十几个选项实现通用表单引擎。

### Renderer 用一致的帧状态

BR-01 说明新增 consumer 后，多处手写 `temporalExperiment || temporalInputProbe` 已容易漏分支。建议保留一个当前帧路由值，统一回答“是否采集时序输入、是否使用历史、是否开启 jitter、如何结束帧”。帧尾推进与诊断统计应分开，不能因为没有启用诊断或旧 TAA 就跳过正常生命周期。

NGX controller 继续由 GPU 线程拥有。CPU planner 与 UI 都只接收小型状态快照，降低锁和对象生命周期相互穿插的成本。这可以同时解决 BR-02、BR-03，不需要增加更多运行模式。

## 五、补对验收缺口，复用已有验证

现有测试已经覆盖不少输入合同、目标提升、alpha、尺寸增长、故障闭锁和退役顺序，应该继续保留。优先补以下空缺：

| 缺口 | 最小补充 | 完成标准 |
| --- | --- | --- |
| 普通 SR/DLAA 的完整帧生命周期 | 可控时钟驱动真实帧首/帧尾，覆盖连续帧和单次长间隔 | 连续帧不持续 reset，长间隔后能恢复 |
| 首次启用与能力状态 | 线程安全状态发布与菜单状态注入 | 请求值、实际值和原因一致 |
| 菜单新增选项 | 开启 DLSS、四档循环、保存重开、隐藏行与非零滚动鼠标映射 | 配置和实际操作一致，截图名称对应正确行 |
| 真实画面 | 同场景、同输出分别检查固定细线、移动、遮挡、新出现物体、字幕/UI、切模式 | 不只记录 Evaluate 成功；保留可比较图像/短片和 reset 状态 |
| 旧执行 fixture | 使用 checked submit/wait 或缩小其验收职责 | 未成功提交/完成时不宣告退役或读回成功 |

修 BR-01 之前先保留当前基线，之后只重跑直接受影响部分。已有 CPU、合成 Vulkan、RTX 路由与打包记录在行为条件不变时可以复用；不因提交、文档修改或重新打包再跑一遍。

对 `motionInvalidity` 的处理先做固定场景检查：当前 NGX Evaluate 没有直接使用这张纹理，但 SDK 的 bias-current-color mask 也不能未经确认就当作等价输入。先判断问题像素来自缺 MV、遮挡、新物体还是 reset，再决定采用已有回退、受控 reset 或合适的 mask。没有图像证据时保持待验证。

## 六、后续性能与维护整理

### 先测量 promotion 分配，再做资源复用

[PrepareSceneCopyDestination:1653](../../LostOdysseyRecomp/gpu/renderer.cpp#L1653) 每次创建 promoted、scratch、composite 三张输出纹理，再按生命周期退休。可以记录每帧创建次数、CPU 创建耗时、在途资源峰值和帧时间，确认成本后按尺寸、格式和已完成 fence 复用。

复用不能跨越尚未完成的提交；分辨率、格式、模式切换仍需正确失效。目标是减少已测得的分配开销，本轮没有 FPS 提升结论。

### SDK 路径与打包保持一个来源

`cmake/LoDlss.cmake` 支持自定义 `LO_DLSS_SDK_ROOT`，但两个 packager 只在两个固定目录寻找许可证。对自定义 SDK 目录的本地构建，运行库已经生成后仍可能在打包阶段失败。建议让 packager 接收同一个 SDK 路径或构建导出的必要元数据，并给 Windows batch 中带空格的 SDK 路径正确引用。

这属于开发便利性，正常 CI 的固定路径已有打包记录，不应据此判定现有公开包缺少运行库或许可证。对打包回归优先验证实际 layout 和必要文件；仅检查 Python 源码里存在某个字符串不能证明最终包内容。

### 明确当前记录与历史检查点

`native-dlss-validation.md` 保留了早期“没有发布二进制”等表述，而 README/CHANGELOG 已记录 v0.6.11 分发。建议把仍有价值的早期段落标记为历史检查点，顶部只保留一个当前状态摘要，并明确链接到版本记录。历史测试结果保留原有适用范围，不因后续发布自动升级成全游戏验收。

本次仅产出两份审计文档；上述改进没有被写成已完成的 roadmap、验收或发布成果。
