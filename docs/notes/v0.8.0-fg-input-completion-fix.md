# P0 input-completion bootstrap and retirement fix

Baseline: `6fc274541a0d469e1836e7bcb1bbfa226f30d59b`, PR #69.
Scope: the standalone Windows Vulkan Streamline/native NGX probe. Production FG
remains disabled; the renderer, P3 resolve selector and guest UI are unchanged.

## Host-side problems addressed

The old explicit-wait experiment entered `eBlockNoClientQueues` immediately on
an FG-on request. Its first missing completion fence/value then forced unknown
ownership and process-lifetime abandonment. The recorded background run did not
execute a timeline wait and cannot establish why the SDK returned no signal.

The new opt-in experiment starts each enable/resize generation with the SDK's
`eBlockPresentingClientQueue`. Only a valid, nonzero SDK completion point observed
in that generation, followed by successful retirement of a **post-Present** queue
marker, permits the next real frame to request `eBlockNoClientQueues`.

This deliberately changes the opt-in diagnostic protocol, not the default probe
mode. A generation without a usable signal stays queue-protected. Missing or
zero signals never count as provider completion or explicit-mode support. If an
FG-on phase never exercises explicit synchronization, the experiment returns
77 (unavailable), not success for the originally requested test.

Once explicit mode is active, a missing or unchanged point is retried at most
32 times on the same present thread, without another frame, tag update, Present
or input write. Each retry is separated by 2 ms. A changed fence, regressed value
or invalid SDK state is rejected. Exhaustion leaves ownership unresolved and
fails closed; there is no unsafe switch back to ordinary presentation. Requiring
an advancing point is conservative: a legitimate skipped frame with unchanged
SDK state may remain unavailable rather than being falsely declared complete.

A failed queue/timeline wait preserves its exact pending state. Cleanup can retry
that same completion once before Off/resize/free; it cannot change modes first or
substitute the earlier render fence. Failed marker submission is unresolved.
Failed Present, invalid state, and unknown ownership do not authorize reuse.

The previous quarantine path retained the Vulkan debug messenger while its
`pUserData` pointed into a destructed App. Its error counter is now separately
owned and quarantined with the retained GPU objects on drain failure. Normal
cleanup still frees it after destroying the messenger.

## Synchronization and ownership

| State | Reuse condition | Failure handling |
| --- | --- | --- |
| Idle | No outstanding FG input use | New real frame can begin |
| Unresolved | None | Same-frame query only; otherwise quarantine on failure |
| QueuePending | Post-Present fence on the SDK-protected presenting queue | Failed wait retains pending marker; no reuse |
| TimelinePending | Exact SDK semaphore/value wait succeeds | Failed wait retains the same point; no reuse |

The empty queue marker is submitted **after** the hooked `vkQueuePresentKHR`.
The ordinary renderer submission fence precedes that hook and cannot prove the
SDK has finished consuming input resources. The optional marker has a separate
fence and is never submitted on the flag-off path. No per-frame `WaitIdle` was
added. The pre-existing lifecycle boundary drains remain unchanged.

`numFramesActuallyPresented` is an interval counter since the last GetState.
Deferred queries accumulate that statistic for the existing diagnostic report;
queries do not advance the real frame token or count as physical frame evidence.
Validation/SDK errors still fail the final exit status and prevent promotion into
explicit mode. They do not suppress a usable completion point needed for cleanup.

Contract source: pinned [Streamline DLSS-G guide, section 15.1](https://github.com/NVIDIA-RTX/Streamline/blob/2122257e0fce486f91b385aa63b9a09b0a34b363/docs/ProgrammingGuideDLSS_G.md#151-how-to-synchronize-the-host-app-dlss-g-inputs-and-streamline-if-required)
and [queue modes / DLSSGState](https://github.com/NVIDIA-RTX/Streamline/blob/2122257e0fce486f91b385aa63b9a09b0a34b363/include/sl_dlss_g.h).
Queue protection here relies on that documented contract; it is not a proof that
the proprietary SDK is free of the previously recorded hazards.

## Checks and reproducible commands

The actual probe calls the SDK-independent `input_completion.h` state machine.
Its 196 CPU assertions cover bootstrap null/zero points, frame/epoch matching,
mode transitions, pending waits, failed submit/Present, stale/changed points,
resize/reset and safe retry. Local GCC 14.2 and Clang 17 builds/runs each exited
0; Clang ASan/UBSan also exited 0. CMake CPU configuration/build and CTest passed
2/2 (ownership plus the existing option parser). Local evidence filenames:
`cpu-configure.log`, `cpu-build.log`, `cpu-test.log`, and
`compilers-and-sanitizers.log`. These are CPU results only.

```sh
cmake -S tools/tests/streamline_fg -B out/fg-input-cpu \
  -DLO_STREAMLINE_FG_CPU_ONLY=ON -DCMAKE_BUILD_TYPE=Release
cmake --build out/fg-input-cpu --config Release --parallel 2
ctest --test-dir out/fg-input-cpu -C Release -V
```

The permanent read-only `Streamline input completion` workflow also builds and
links the **actual** Windows probe with the manifest-verified Streamline 2.14.1
archive and pinned native NGX SDK. It does not run the NVIDIA probe on hosted
runners or upload vendor DLLs. Windows/Linux CPU contracts are separately run.

The Linux Vulkan fixture exercises native queue fences and timeline semaphores
with the same state machine. It demonstrates an already-signaled renderer fence
while the modeled post-Present queue gate remains pending, null-signal protected
retirement, real timeline timeout and successful retry. The gate is a modeled
SDK wait, not a Streamline call, WSI present or generated frame. The fixture
requires Khronos validation and requests synchronization validation.
