## Decision

TAA, DLSS Super Resolution, and temporal FSR are technically plausible, because this project owns the translated shaders, guest draw dispatch, GPU depth surfaces, and D3D12 command lists. They are **not presently ready for a production settings switch**. The main work is recovering a coherent scene and temporal-input contract. Connecting a vendor SDK is a later step.

The existing presentation pass receives a final resolved color image, with the game's UI already potentially composited. It cannot provide reliable depth, object motion, or rendering jitter by itself. A post-presentation accumulation filter would have a substantially weaker contract than the requested TAA. Optical flow and all-zero vectors must not be described as native motion vectors.

For v0.4.0 planning, keep SMAA/spatial presentation scaling independently deliverable while treating TAA as a gated implementation track sharing its foundations with the requested DLSS/FSR research. No evidence from this investigation establishes that TAA will necessarily improve text clarity; protecting the text/UI path is a separate requirement.

## Verified vendor contracts

Official sources were checked live. Context7's `streamline` lookup returned unrelated icon/Home Assistant libraries, so the investigation used NVIDIA and AMD primary documentation and headers directly.

### DLSS through Streamline

The checked DLSS guide identifies itself as Streamline **2.12.0**. Required resources are render-resolution input color, depth, motion vectors and output-resolution color. The SDK queries the preferred render dimensions for the chosen output dimensions and mode. Frame token and viewport must match between options/constants/tags/evaluation. Resource extents and lifetime matter, and the host must restore command-list state after evaluation. Exposure may be supplied or auto exposure used. [NVIDIA DLSS integration guide](https://github.com/NVIDIA-RTX/Streamline/blob/e8aaa6eaac968711fb62473d4ae8256dde20919b/docs/ProgrammingGuideDLSS.md)

The common constants carry unjittered row-major projection/reprojection matrices, camera parameters, pixel-space jitter, reset, depth inversion and MV metadata. For **input-pixel** vectors Streamline specifies `mvecScale = (1/renderWidth, 1/renderHeight)`; that is not NGX's direct pixel conversion. Set `cameraMotionIncluded`, `motionVectorsJittered`, `motionVectorsDilated` and invalid-value handling to match the actual data. [NVIDIA constants header](https://github.com/NVIDIA-RTX/Streamline/blob/e8aaa6eaac968711fb62473d4ae8256dde20919b/include/sl_consts.h), [DLSS scale examples](https://github.com/NVIDIA-RTX/Streamline/blob/e8aaa6eaac968711fb62473d4ae8256dde20919b/docs/ProgrammingGuideDLSS.md#60-provide-common-constants)

The current direct NGX D3D12 helper independently defines render-pixel jitter and MV scaling **to pixel space**; its default scale is 1. Thus input-pixel vectors use NGX scale `(1,1)`, whereas a Streamline adapter normalizes those same vectors. The helper also exposes pre-exposure, exposure scale, subrects and reset; some other fields are explicitly reserved or research-only. Do not assume those fields implement FSR's reactive-mask semantics. [NVIDIA NGX helper](https://github.com/NVIDIA/DLSS/blob/main/include/nvsdk_ngx_helpers.h)

Motion must point from the current pixel toward its previous-frame location, not forward along movement. NVIDIA's current programming guide describes reversing the scale when the source points in the other direction. The guide is dated 31 March 2026; its search-indexed motion-vector section was available, although the PDF's full text could not be opened by the browser tool. No other details here rely on unavailable PDF content. [NVIDIA programming guide, section 3.6.2](https://raw.githubusercontent.com/NVIDIA/DLSS/main/doc/DLSS_Programming_Guide_Release.pdf)

### FSR 3 and FSR 4 need separate capability records

AMD's current SDK page lists **FSR SDK 2.3**, with analytical FSR **3.1.5** and ML upscaling **4.1.1**. It documents D3D12, signed binary distribution and ML support for RX 9000/7000 discrete GPUs, with analytical fallback paths for older hardware. Do not infer FSR 4 support for the user's NVIDIA GPU or an AMD APU from shader-model support alone. Query and record the chosen provider, hardware/driver support and actual backend. [AMD FSR SDK](https://gpuopen.com/amd-fsr-sdk/)

FSR 3 takes current render-resolution color/depth, backward 2D motion in pixel units, and display-resolution output. MV texture resolution may instead be display resolution with the corresponding flag. Depth inversion/infinite projection flags must describe the data. Jitter applies to scene inputs, normally not MV; jitter-cancellation is available for jittered vectors. Reactive/T&C masks are optional inputs that improve difficult transparency/animated shading; particle coverage is especially relevant. It replaces a separate TAA stage. Tonemapping, grain and several post effects are generally placed afterward. [AMD FSR 3.1.5 guide](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-upscaler/)

The API also requests actual `renderSize`/`upscaleSize`, elapsed milliseconds, positive `preExposure`, camera near/far, vertical FOV and view-space units. It provides queries for dimensions/quality and jitter phases; the API distinguishes texture extent from render extent. Use pixel MV scale `(1,1)` for a canonical pixel field. [AMD upscaler header](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/include/ffx_upscale.h)

FSR 4.1.1 requires the FSR API and signed distribution, prefers linear input color, and supplies an explicit nonlinear-color option when necessary. Reactive/T&C masks are no longer required by FSR 4; query resource requirements instead of generating masks unconditionally. Exposure and pre-exposure differ: pre-exposure recovers the original signal before exposure is applied. This does **not** remove the need for valid motion/depth/jitter or prove that our transparency path is acceptable. [AMD FSR 4.1.1 guide](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/techniques/super-resolution-ml.md)

The pinned documentation heads were obtained from GitHub during this investigation: Streamline `e8aaa6eaac968711fb62473d4ae8256dde20919b`; FidelityFX `60f4ea81909200d8542eca14dccb2628b763a9a3`. These are documentation references, not dependencies installed in LostOdysseyRecomp. Before implementation choose a tested release package and record its binary versions/digests. Check the applicable distribution terms/app-ID setup for that package rather than assuming an open-source framework licenses every bundled model binary.

## Proposed common contract

This section is a project design proposal, not an existing API or measured result.

Use one `TemporalFrameInputs` bundle whose required fields are validated before dispatch:

- Frame/current-previous IDs and discontinuity reason; valid scene-view ID; actual elapsed time between rendered frames.
- Current scene color plus color-space/HDR/pre-exposure metadata; depth from the same scene stage and its projection convention; actual render extent and target content extent excluding letterbox bars.
- An unjittered current and previous camera transform; render-pixel jitter actually applied to this frame; a history generation/epoch for resize or scene transitions.
- A canonical backward motion field in **render pixels**, X right and Y down, plus validity and coverage information. Convert units/sign once in each SDK adapter.
- Optional material/reactivity inputs and an identified UI composition point; no fabricated exposure, depth or camera constants.

For a surface currently at `(100, 100)` that was at `(98, 100)`, the canonical vector is `(-2, 0)`. A current pixel `(x,y)` samples previous history at `(x,y)+mv`. Use synthetic one-pixel translations, both camera and object tests, to verify adapters. If producer outputs normalized UV differences, multiply by the actual render dimensions first. If producer outputs conventional clip NDC differences, the X/Y conversion includes the viewport's half-scale and Y inversion; never copy a vaguely labeled NDC example without verifying its convention.

Unjittered clip positions produce the geometry MV; current jitter moves raster sample locations. As a proposed host-side implementation, for canonical jitter `j` in render pixels, add `(2*j.x/W, -2*j.y/H) * clip.w` to **validated final host clip XY**. Keep this distinct from Xenos's fixed half-pixel offset. All geometry contributing to that scene view must agree, including its depth path and relevant translucent geometry. Do not apply camera jitter to shadow-map rendering, UI, clear rectangles or arbitrary full-screen triangles; adjust the relevant full-screen reconstruction/sampling mathematics instead. This is why the shader epilogue is only a candidate hook until the pass classifier is proven.

Freeze and retain per-object/instance previous transform and previous skin/deformation inputs at a consistent guest-render boundary. A motion-only pass can run the same vertex math twice with the two snapshots and rasterize with current geometry/depth. This avoids requiring a universal decomposition of every bone matrix, but still requires trustworthy object matching and previous stream/texture/constant contents. The alternative of appending MV output to existing scene shaders needs extra interpolators, render target formats, pipeline keys and correct PS discard coverage. Compare both approaches using one static mesh and one skinned mesh before changing all translated shaders.

Camera-only depth reprojection is a useful first probe for static geometry. It cannot establish motion for walking characters, moving objects, skinning, particles or animated textures. Explicitly label that coverage and invalidate unsupported pixels. Optical flow may later be evaluated as a supplementary approximation, but it is outside the native-input acceptance gate.

The phase-3 tolerance is an initial proposed engineering threshold, not a vendor requirement or achieved result. Image metrics should separate static geometry, moving geometry, disocclusions and UI; a whole-frame average cannot detect a missing spark or a blurred glyph.

Reset on first valid frame, camera cut/map load, view/projection change, resource reallocation, incompatible render/output size or quality change, AA/upscaler toggle, loss of a valid frame pair, and menu/video transitions without compatible scene inputs. Pause/resume policy must follow whether the guest actually produced new coherent scene frames. Repeatedly presenting the same image at 120 Hz must not advance the temporal sample sequence or count as new input history.

## Feasibility and v0.4.0 risk

- **Good starting position:** direct GPU ownership, raw depth resolves, translated shader access, full constant banks, existing selected-resolve tracing and offline vertex replay.
- **Highest uncertainty:** stable scene/UI boundaries and object/instance history. These require game-specific reverse engineering; no generic DLL or post-process flag recovers their semantics.
- **Moderate implementation cost after proof:** a native D3D12 SDK adapter, resource-state transitions, context lifetime, runtime capability detection, quality settings and diagnostics.
- **Separate substantial change:** genuine internal-resolution scaling. Current EDRAM layout, guest texture fetches, half-pixel rules, resolves and post-process constants assume guest dimensions. Changing the swapchain alone does not satisfy this requirement.
- **Shared TAA benefit:** validated jitter, depth, motion and history can serve TAA and both temporal-upscaler families; build that contract once. Vendor upscalers should replace the scene TAA stage rather than stack another history filter behind it.
- **No release claim:** this report supports a staged feasibility plan. It proves neither temporal image quality nor frame-time improvement, and it does not establish native MV, an enabled TAA mode, DLSS support, or FSR support in the current game build.
