## Current conclusion

**Fixed and confirmed by the user listening to it.** A frame tail that crossed packets used to cause the new frames of the continuation packet to be skipped, so dialogue played at nearly double speed. After the fix, for the same armored vehicle segment, the time ratio between the game mix and the original dialogue is 1.000. All 4062 frames were fully recovered, and the 34 multichannel input buffers, totaling 4264 frames, had no decode errors. Build 135DCA79 was installed. The save and profile were not changed. Full-game audio, loop subframes, and the opening WMV are still outside the scope of this complete verification.

`LO_AUDIO_DIAGNOSTICS=1` enables counts for decode, skip, write, error, and explicit cursor updates for each XMA context. The SDL queue log also records drops and commit errors. Private audio and recordings are kept only in the local, git-ignored out directory.

For the current summary, see the [work report](../archive/WORK_REPORT_2026-09-05.md) and the [status overview](../STATUS.md). The sections below keep the evidence in the order of the experiments. Early unfinished states do not represent the latest results.

`apu/xma.cpp` assembles compressed frames from 2048-byte packets in the alternating input buffers. It calls the XMAFRAMES decoder, converts the 512-sample decoded output to the big-endian interleaved int16 that the guest expects, and writes it to the output ring in 128-sample subframes. `apu/audio.cpp` downmixes the 6-channel planar big-endian float that the game finally submits to 48 kHz stereo PCM, and outputs it through an SDL queue. The device buffer has a limit, callback catch-up is bounded, and non-finite values are set to zero.

Update of 2026-10-07 (merged into main, not yet released; latest release v0.8.44): the downmix above is the default "stereo" output, and its bytes are unchanged. The sound settings add "Audio output: Stereo / 5.1 surround" (`audio_output`, switched immediately, [PR #271](https://github.com/freefrank/LostOdysseyRecomp/pull/271), merged at 2026-10-07T03:35:13Z as `a5fa8961`, Issue #174 closed). In 5.1 mode, the game's six channels (FL, FR, FC, LFE, BL, BR, in the same order as SDL's 6-channel layout) are interleaved and sent directly, with no downmix. If the device has fewer than 6 channels, it falls back to the stereo downmix and writes a log line. 7.1 devices are mapped by SDL. This PR was checked on psvita (Proton/WASAPI, with recording from a null output). It verified the six-channel output, that the folded result matches the stereo recording within 0.1 dB, the fallback on a two-channel device, and the 7.1 device path. Real 5.1 speakers and native Linux, macOS, and Android audio were not tested. A user in the Issue said they could test. For details, see the [settings menu](settings-menu.md).

FFmpeg comes from `https://github.com/xenia-project/FFmpeg`, at the fixed commit `15ece0882e8d5875051ff5b73c5a8326f7cee9f5`. CMake FetchContent fetches the source. The explicit source file list in `thirdparty/ffmpeg.cmake` builds avcodec/avutil, keeping its configuration and original copyright headers. The license text is COPYING.LGPLv2.1 in the fetched source. Each source file keeps its own license. The release packaging step is not finished. It needs the dependency licenses and the matching source or relink materials. There is no release binary yet.

## User retest and loop end correction

In the diagnostic build, PID 10672, the user reported that background audio and some dialogue disappeared, while other sounds were still normal. The lighting defect did not change. In the real log `out/build/windows-clang/LostOdysseyRecomp/logs/runtime-1788588572991415.log`, the audio peak dropped to zero between 101 and 121 seconds. The investigation found that the loop check only accepted `readOffset == loopEnd`. The last frame could jump straight into the next packet and skip over the end point. The old code also invalidated an exhausted input buffer before checking the loop. Following the local Xenia reference at `out/audio-reference/xma_context.cc` (`TrySetupNextLoop`), the code now jumps back when it reaches or passes the end point. It keeps the loop input before switching buffers and clears the cross-packet skip count. Finite loops count down. Infinite loops with 255 stay at 255.

A new `LoXmaLoopTest` was added. It uses 219 packets from a real context, with the end point at bit 3580323, to verify tail-packet crossing. It also checks finite loops, infinite loops, that there is no early jump back, and empty loop ranges. The test and runtime build passed. ## Positioned read race on a shared file handle (2026-09-05)

The original `NtReadFile` implementation called _fseeki64 and then fread on the same FILE*. The CRT lock for a single call cannot protect the file position between the two calls. An integration regression was added using a real guest import. Four threads shared one handle returned by NtCreateFile, each reading a different offset, 2000 times per thread. Each read was compared byte by byte against the original payload pattern. In the unfixed version, 932 out of 8000 requests did not match. The log is out/storage-concurrency-before.log. The test did not change the scheduling or add delays to the implementation.

FileHandle gained a per-handle ioMutex. It covers NtReadFile, NtWriteFile, NtReadFileScatter, and the position and size query changes and flush. It does not serialize different handles, and it is not a global lock. File-open initialization happens before the handle is published. Close concurrency and handle reference lifetime are not in scope for this fix.

After the fix, the same test had 0/8000 errors. A CREATE_ALWAYS overwrite and a new-process read-overwritten test also had 0/8000 errors. The original integration regressions for save metadata, events, thumbnails and so on passed. See out/storage-concurrency-after.log, storage-concurrency-overwrite.log, and storage-concurrency-read-overwritten.log. The runtime build B8DBBBD9 passed. The test covers the correctness of concurrent positioned reads. It does not prove that the missing sound or the GPU crash in the game was caused by this. Real track verification is still pending. Not committed.

## XMA command register overwritten by the last write (2026-09-05)

Following the stereo non-advancing clue, the investigation located the actual guest loop 82CC5B58. For each hardware context, it writes one bit to the 7FEA1940 group register on its own (stwbrx/eieio). Writing the same group three times in a row should enable three contexts. The old LoMmioStore32 did only a plain assignment. The XMA worker exchanges the last value every 250–1000 microseconds, so earlier requests could be lost. The lock 82CC58E8 and the clear are also written as bit commands. This is not a volume or FFmpeg packet parsing problem.

Compared with WriteRegister in https://raw.githubusercontent.com/xenia-project/xenia/master/src/xenia/apu/xma_decoder.cc: each write calls context.Enable/Disable/Clear separately. Disable/Clear share a mutex with Work. A new apu::xma::WriteCommand processes the three command groups before the normal MMIO mirror write. It changes state one bit at a time according to this write's mask, with lock and clear done synchronously. The worker now scans the enabled contexts instead of taking the last register value. The existing g_mutex serializes Work and commands. This avoids only ORing bits and reordering kick/lock/clear. The simulated read of the XMA status register is still incomplete, so this does not claim full hardware timing.
