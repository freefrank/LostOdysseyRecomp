# v0.5.0 QOL 需求与未来验收标准

本文记录 v0.5.0 规划中的 12 项 Windows QOL 需求，并保留各项需求与验收标准。文件最初建立时仅用于需求记录；本页的历史总结对应 v0.4.19 candidate 的限定成果，13 个功能批次已提交至 v0.4.15，最终提交为 `f77d943261e14105d17c880ffa40c171b4191dcc`，完整序列见 `out/commit-batches/ledger.json`。QOL1–QOL12 均有对应的限定验证，其中 QOL6 保留 v0.4.17 原安装目录候选的两次 D3D12 `prepare-only` 启动验证，用户已确认当前 D3D12/Vulkan 场景可用，但未确认更广泛的玩家启动验收。当前发布基线仍为 v0.4.2，证据与边界见[项目状态](../STATUS.md)及 `out/v0.5.0/` 报告。

交付状态：v0.4.19 runtime build 仅作为历史本地候选记录，未部署；v0.4.17 仅保留为可回滚的本地开发候选。发布基线仍为 v0.4.2，v0.4.15 开发包仅保留为历史证据。正式 installer 冻结介质／DPI 广度、多平台 updater 交付、玩家验收和全游戏覆盖仍未完成。

当前完成项：QOL1 保留 ISO/GOD/解包文件夹/独立 XEX 读取和导入前识别复核，限定导入检查及 15 文件合成导入流程通过；只接受已审计 XEX SHA256，未知哈希仅作诊断。QOL2 空 `game-path.txt` 使用 EXE 旁的 `../game`。QOL4 直接启动发现根目录 `default.xex` 或配置／导入根下的 `disc1`，并按记录回退到 `game/disc1`、`game`、EXE 及 EXE 上级目录的 `game`；显式非空 `--game` 优先且保持隔离，坏的显式配置不静默回退。完整游戏、全 DPI 矩阵和完整通关仍未验证。

用户已确认当前 D3D12/Vulkan 场景可用；Windows Vulkan 的既有证据仍限于 RTX 5080 的 Maps 2、3、12，且 Map2/3 与 Map12 使用不同冻结候选及证据范围，不能合并为同一 binary 结论。这不能替代完整游戏、其他 GPU、完整视觉或发布验收。后端选择的能力、失败回退和设备探针专项检查已通过，v0.4.19 runtime build 已完成为本地候选但尚未部署；DX11 仍不支持运行时。性能记录、菜单、更新器和捕获证据仍按各项边界分别计算。

## 需求清单

1. **Installer 适配安装来源与目录结构**

   Installer 应能处理不同文件夹结构、ISO、已解包文件夹和单独 XEX，并可选用 MD5/SHA256 做版本识别；界面需要清晰、美观并说明识别结果。未来验收至少覆盖这些输入的成功、版本不匹配、缺失文件和取消/重试路径；错误应提供可恢复提示。路径搜索以显式用户选择优先，并覆盖当前 EXE 目录与空路径的 `../game` 候选。

2. **`game-path.txt` 默认路径**

   当 `game-path.txt` 为空时，默认使用相对于当前 EXE 目录的 `../game`。显式配置仍优先；未来验收需覆盖空文件、有效显式路径、相对路径解析和无效路径提示，并确认不会误读工作目录之外的旧配置。

3. **Recomp EXE 图标**

   `LostOdysseyRecomp.exe` 必须使用突出 Recomp 身份的 Windows 图标；可以采用原游戏图标改造的方向，但不是硬性实现方式。未来验收需检查 Explorer、快捷方式、任务栏和安装包中显示的图标与架构资源是否一致。

4. **EXE 直接启动与资源定位**

   用户应能直接运行 `LostOdysseyRecomp.exe`，无需旁边的 `.bat` 或 `.cmd`；资源默认从当前 EXE 目录定位，并遵守显式路径优先规则。未来验收需覆盖从资源目录、快捷方式和不同工作目录直接启动，以及缺失资源时的可恢复错误提示。

5. **独立、现代化的首次启动配置界面**

   首次启动配置菜单应从当前流程中独立为现代化界面/模块，便于选择语言、资源路径和初始图形设置。这里的“独立”指界面与模块边界，不要求额外 EXE。未来验收需确认首次启动、取消/返回、重复启动和配置保存路径之间的行为一致。

6. **区分启动时 shader 准备阶段**

   用户反馈每次启动仍显示 `compiling shader cache`。目标是避免不必要的重复编译：有效缓存应复用，只编译缺失或失效的项目。后续工作必须先区分缓存读取、资源发现、PSO 预热、实际 shader 重编译和仅显示旧提示的情况；`Compiling` 字样本身不构成全量重编译实证。未来验收需用日志或等价可观察证据说明每个阶段的实际发生次数，并覆盖缓存已存在与缓存失效两种启动。

7. **shader 编译线程数**

   编译线程数规则为逻辑线程数减一，最小为 1。该规则已有历史实现记录；后续应核实当前启动路径是否完整覆盖，必要时修复并进行相称验证。未来验收需覆盖单线程、双线程及更多逻辑线程环境，并确认不会创建 0 或负数线程。

8. **轻量、现代化的 Debug Menu**

   Debug Menu 应保留现有诊断能力，同时采用轻量、现代化的布局和交互，避免阻塞正常游戏操作。未来验收需覆盖打开/关闭、键盘与手柄焦点、滚动/缩放、状态读取以及现有捕获和诊断入口；诊断失败应仍可返回游戏。

9. **以项目设置菜单替换内置菜单的可行性**

   评估在可行时用项目设置菜单替换内置菜单。该项先经过可行性门槛：资源/输入/保存契约、原版流程依赖、兼容性和回退路径必须有证据；未通过门槛不得宣称已替换。未来验收需保留安全回退，并覆盖设置保存、取消和返回游戏。

10. **设置菜单忠实复刻原版风格**

   设置菜单以忠实、完整复刻原版游戏风格为目标。它与第 5 项的现代化首次启动布局是不同目标：首次启动强调清晰配置，设置菜单强调原版呈现与行为；实际可达程度由未来视觉验收确认。未来验收需分别比较布局、字体、层级、选中态、确认/取消和输入行为，不以现代化首启界面代替原版风格验收。

11. **需要重启的设置提示**

   对需要重启才能生效的设置，界面应明确提示并询问是否立即重启；用户选择稍后时应安全保存并继续，选择立即重启时应走受控重启流程。未来验收需覆盖确认、取消、重复提示、保存失败和重启失败恢复，且不得损坏存档、配置或游戏数据。

12. **启动检查更新与多平台资产选择**

   当前 Windows 启动检测到较新的匹配版本后，应从 GitHub 自动下载 binary 并更新；已有最新版时不应每次重复下载。GitHub 版本比较和 asset 选择机制属于未来设计；未来 macOS 与 Linux 使用对应平台资产（包括 AppImage）后再扩展。下载应先暂存并校验，退出后通过原子替换或 helper 完成更新；下载、校验、替换失败时应恢复并保护存档、设置和游戏数据。离线或 GitHub 不可用不得阻止启动。若没有公开 Release/version 资产，程序不能凭空获取更新，也不因此创建新的发布要求。未来验收需覆盖已是最新、可用更新、错误校验、断网、权限不足、回滚和多资产选择。

## 版本规则与范围

- 当前发布版本保持 `v0.4.2`；v0.5.0 是规划里程碑，不要求本轮或每项需求完成时直接 bump 到 `v0.5.0`。
- 每项 feature 只有在实现完成并通过相称的必要验证后，才按当前实际版本增加一个 patch（`+0.0.1`）；这不要求同时发布 Release。仅记录文档、讨论或未完成实现/必要验证的实验不增加版本；用户验收与必要验证分别记录。
- 文件初始建立时的“本轮只记录”描述属于历史语境。当前状态是：未发布源码 0.4.17 保留 QOL1–QOL12 的限定验证及 bounded Windows Vulkan 验证；QOL6 已完成原安装目录两次 D3D12 `prepare-only` 启动验证，用户验收仍未确认。实现、验证、用户美术验收和发布状态仍分别记录。当前发布基线仍为 v0.4.2，未创建新的 Release、tag、commit 或 push。
