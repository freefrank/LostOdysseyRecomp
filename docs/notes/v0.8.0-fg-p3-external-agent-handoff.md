## 本次下一步目标

实现 producer snapshot 与实际 final resolve/present packet 的精确关联，形成可检查、可取消、可回收的 P3 诊断交接。

第一阶段保持诊断模式默认关闭，不开启完整 provider FG。

交接对象必须包含：

1. 同一真实渲染帧的 `frame_id` 与 `history_epoch`。
2. source allocation identity。
3. source write generation 或等价的写入版本。
4. resolve identity，以及实际参与 final present 的 resolve 记录。
5. 实际 plan/output extent、格式和必要的 color/depth/MV metadata。
6. producer submission serial、completion fence/timeline 与取消状态。
7. packet 与 consumer 的明确 ownership。

不得通过全局 latest snapshot、裸指针、时间戳、guest address、单一 frame number 或任意 draw ordinal 关联。guest address 可以复用；同一帧也可能有多个 allocation、resolve 或 plan。

snapshot 必须只在 source allocation、write generation、resolve identity、frame/epoch 和输出计划均相符时交给 consumer。任何字段未知、冲突、跨 epoch 或已取消时，交接为 unavailable，并继续普通 present。

`PresentFrame.ProviderReady` 不能单独证明 producer GPU 已完成，也不能证明跨帧输入一致。交接处必须明确 producer submission/completion 与未来 provider completion 的区别。

不要加入无条件的每帧 `WaitIdle`。使用有界的 in-flight 持有；达到容量、取消、resize、mode switch、cut/reset、device loss 或退出时，按状态机取消未提交项并保留已提交项直到其 completion 条件成立。

submit 失败必须释放或丢弃对应 packet，不能让旧 snapshot 被错误复用。wait 失败应保留 pending 状态并使 consumer 不可用，不能强行标记 completed。

普通 present 在 snapshot 不可用、关联失败、超容量或 provider 未启用时必须继续工作。

上述回退限于 FG 诊断失败；真实 GPU/device 错误必须遵循现有 `GpuWorkStopped` 停止规则，不能为继续 present 绕过已失败的提交路径。资源引用保活也不等于像素不可变：consumer 完成前，所引用的 final resolve 必须不会被下一次写入覆盖，或持有其独立副本。

## 真实路径约束

当前 `AcquireResolvedSurface` 返回 raw final texture 和 optional `FramePlan`；它还没有接入 `PresentLeaseQueue`。

当前新 snapshot 只保留内部 `shared_ptr`，尚未形成公开 producer handoff。

已核对的调用路径可作为入口：`command_processor.cpp` 先调用 public `renderer::Flush()`，再进入 `video::PresentFrontbuffer`。后者先通过 `PreparePresentation` 处理 resize/minimize；GPU、非 CPU present、非 menu 分支调用 `AcquireResolvedSurface` 取得 resolved texture，随后等待上一批 present GPU、获取 swapchain image、合成、提交并 present。内部 `Renderer::Flush()` 还可能在帧中间提交；public flush 成功后会推进 renderer frame。

本阶段至少完成一条生产 renderer → resolve → video 交接路径的正向 fixture，并以真实代码传递的身份作断言。仅增加一个独立数据结构、只做 CPU 比较测试，或让所有输入始终 unavailable，不构成本阶段完成。

不要把 host settings/debug menu 的 CPU upload 分支当作客端 HUD 分离证明。它属于宿主覆盖层路径，与 guest HUD、字幕、战斗 UI 和透明效果不同。

现有 `ResolvedSurface` 已有 `frame`、`writeOrdinal`、write rectangle、`sourcePlan`、`sourcePlanValid` 等字段；`HostTexture` 已有 allocation serial。优先复用这些 provenance 字段和现有 `present_capture` ticket 的 exact capture identity 模式，避免先建一套广泛的 shader tracking framework。

`NewestResolved` 目前按 `rs.frame >= best.frame` 选择 format variant；`writeOrdinal` 不等于它的选择依据。因此仅比较 guest address、frame 或 write ordinal 不能证明 snapshot 对应当前 final resolve。若 lineage 缺失，应交接为 unavailable 并走普通 present；不要在默认路径强行补全或悄悄改 selector 语义。

public flush、内部 mid-frame submit、present packet 和真实 game frame 可能出现 off-by-one 或 batch 边界差异。关联字段必须记录这些边界，不能把 command batch 编号直接当作真实 frame ID。

缺少 resolve lineage、source plan、allocation serial 或写入 generation 时，跳过 FG packet 并保留 ordinary present。menu、`LO_PRESENT_CPU`、missing resolve 等 fallback 都应继续普通呈现。

需要先沿现有 renderer/presentation 调用路径找出：

- `RecordSceneCopyDlssUsing` 成功后的 continuation。
- source texture 的 allocation 与写入 generation 产生位置。
- resolve identity 和 final present packet 产生位置。
- submission serial、producer fence/timeline 和 wait/cancel 处理位置。
- `AcquireResolvedSurface`、`PresentFrame`、`PresentLeaseQueue` 之间的真实边界。

不要把 `srApplied` snapshot 当作 HUDless 输入。它可能包含 postprocessing，也可能含有未知 UI。

scene candidate 的格式不能证明 color semantics。不要因纹理格式或名称直接宣称它是最终颜色、HUDless 颜色或可供 provider 使用的输入。

## UI 边界

当前 `UI=Unavailable` 必须保持，直到有独立的捕获证据证明真实 UI 分离。

`NoUi` 需要明确证据，不能作为默认猜测。

不能从最终屏幕减去另一张图来猜 alpha。

不能用任意 draw ordinal、纹理地址或单个 shader 标识代替 UI 归属证明。

下一步 UI 工作分三步：

1. 发现实际 UI/字幕/菜单/透明效果的资源和提交边界。
2. 在输出分辨率验证 HUDless color 与 straight-alpha UI 的真实来源。
3. 只有输入、生命周期和 P0 SDK 问题分别有证据后，才接入 provider/Reflex。

provider/Reflex 是独立后续 lane，不应被描述成当前 P3 snapshot 的已完成部分，也不应把 P0 SDK 未解决问题写成 P3 代码本身的失败。

## 兼容与未覆盖范围

当前 snapshot 只覆盖成功 SR scene recording 路径。

AA、TAA、无 SR、失败 SR、首次帧、历史 reset、resize、切换呈现模式、device 重建和多帧在途仍需明确覆盖。

其中无 SR 和非 SR 路径应先判定是否有同等资源 identity/generation/resolve 证据，再决定是否支持；不能用 SR snapshot 代替。

现有 GPU snapshot 测试已经验证：原始资源在同一 batch 被覆盖后，副本像素保持不变。

现有 renderer 测试已经验证：synthetic vendor、default-off、accepted/failed SR、submit rejection、failed fence wait 等状态。

不要仅为交接重复这些测试。只有当实现改变对应行为，才增加或重跑最小测试。

## 新增测试建议

新增测试应优先围绕关联合同，而不是复制实现：

- matching allocation/write generation/resolve/frame/epoch 成功交接。
- reused guest address 或 allocation 被拒绝。
- source generation mismatch 被拒绝。
- resolve identity mismatch 被拒绝。
- frame 或 history epoch mismatch 被拒绝。
- cut/reset、resize、mode switch 和 cancel 清除未提交 packet。
- submit failure 不污染下一帧。
- wait failure 保留 pending 且 consumer 不可用。
- 最后一个 consumer release 后资源正确回收。
- bounded in-flight 超限后普通 present 仍继续。

测试必须记录实际覆盖和未知项。不要把 synthetic vendor、应用 Present 次数或 packet 创建成功当作物理显示、provider 完成或玩家验收。
