# v0.4.0 development scope

Defined on 2026-09-07. **v0.4.0 is local development, not a release.** The scope table describes acceptance targets; the dated checkpoint below distinguishes implemented changes from outstanding work. The current published baseline is [v0.3.0](https://github.com/freefrank/LostOdysseyRecomp/releases/tag/v0.3.0). Its public release record was checked on this date; the planning checkout is `239e851` with pre-existing local changes.

The user selected automatic output-resolution matching with quality presets. The user also reports an existing closed-source implementation with correct gameplay speed at higher frame rates; its name, exact frame-rate coverage and implementation have not been supplied. This is a useful feasibility lead. The latest user feedback prioritizes stable 60 FPS with correct gameplay speed; 120 FPS is an optional stretch goal that may be deferred if difficult and does not block v0.4.0 delivery.

## Scope and acceptance

| Work | Intended behavior | Acceptance evidence |
|---|---|---|
| Text rendering clarity | Correct game glyph rendering and crisp host UI at the selected output size | Paired raw/presented captures of the same text, with native-resolution/AA-off controls; compare readable glyphs, spacing, outlines and motion stability across supported language samples |
| Bilingual Debug menu | Immediate English / Simplified Chinese switching, persisted independently of game language; Capture render state placed at the top | Static labels, live statuses, help and capture results update; no missing glyphs or clipped controls; switching preserves inputs, selections and settings preview/rollback behavior |
| SMAA | Spatial SMAA 1x as an alternative to Off/FXAA | Reference edge/blend/final images, diagonal and subpixel features, flat-region preservation, actual game text and scene comparisons |
| TAA | Temporal antialiasing with valid reprojection and controlled history | Verified scene color/depth, current/previous motion and jitter; camera/object motion, disocclusion, camera cuts, resize and menu transitions without persistent trails |
| Resolution-aware upscaling | Match the real output viewport automatically, with quality presets and aspect preservation | Report actual render/input/output sizes; test native, larger and smaller outputs, resize and display-mode changes; preserve UI clarity |
| 60 FPS; optional 120 FPS | Prioritize stable 60 FPS while preserving gameplay speed; retain the experimental 120 FPS candidate as optional work | Unique game-frame cadence and frame pacing plus equal-wall-time movement, animation, Ring timing, effects, audio and cutscene checks against 30 FPS; apply the same checks if 120 FPS is pursued |
| DLSS/FSR research | Determine whether reliable temporal upscaling inputs and SDK integration can be supplied | A versioned input contract, sampled buffers and reprojection results, integration cost, hardware coverage and explicit remaining gaps |

DLSS/FSR integration is a research deliverable in this target; the [versioned feasibility report](temporal-upscaling-feasibility.md) preserves the official contracts, current input evidence and future implementation route. Experimental camera-based TAA is selectable with bounded actual-game and menu Apply/Keep/reopen validation; broader image quality remains regression coverage. Correct-speed, stable 60 FPS is the frame-rate acceptance priority; 120 FPS may be deferred without blocking v0.4.0. A selectable option alone does not establish either result. Frame generation, ray reconstruction, ultrawide FOV changes and cross-edition language patches are not added by this scope.

### Text and output scaling

`gpu/presentation.cpp` currently combines linear color sampling and optional FXAA in one fullscreen draw. `gpu/video.cpp` supplies the final resolved game image. Changing the output size does not change guest render targets. The host Settings page is rasterized at a fixed 1280 × 720 in `settings/menu.cpp`, then enlarged by the same presenter; it already bypasses FXAA.

First separate the reported in-game glyph problem from host-menu rasterization and final resampling. Capture the same text before and after presentation at 1280 × 720, then at 1920 × 1080, 2560 × 1440 and 3840 × 2160. For game text, identify the contributing draw, font atlas, UVs, sampler and mip behavior before changing them. A higher-resolution host UI can remove its own rasterize-then-enlarge step, but is not evidence of a game-font repair. Global nearest filtering or indiscriminate sharpening would obscure the diagnosis.

Introduce a presentation policy that receives measured source extent, actual output viewport, AA mode and scaling mode. Native-size presentation should avoid unnecessary resampling; downscaling needs an appropriate reduction path; upscaling should operate once at the correct stage. Resize/display changes invalidate size-dependent resources. Preserve aspect ratio and letterboxing.

Quality/Balanced/Performance are proposed user-facing presets. Their internal-size ratios must belong to the selected backend, be rounded to its alignment requirements and reflect the render targets actually produced. Fixed 720p input must not be relabeled as several different internal resolutions. Implementing adjustable scene render resolution requires auditing viewport/scissor, render-target/depth allocation, resolve coordinates, aliases and post-processing constants. A spatial scaling prototype can run earlier using its measured fixed source, with that limitation stated.

### Debug menu

The Debug menu already uses Win32 Unicode APIs. Add an independent persisted `debug_language` value and a translation layer covering controls and live battle, teleport, POI, map and capture statuses. Translate POI category display without altering category keys used by scan logic. Preserve guest-provided localized map names and output paths. Existing Settings previews save whole configuration snapshots; prevent those snapshots from overwriting a Debug-language change made during a display preview.

### Antialiasing and temporal inputs

SMAA 1x is the first spatial implementation: use the upstream edge-detection, blending-weight and neighborhood-blending passes with its lookup textures, size metrics and color-space rules. Compare intermediate buffers against the reference. Temporal SMAA T2x is a distinct mode requiring jitter and temporal resolution; it does not make a history-free implementation TAA. See the [SMAA author reference](https://github.com/iryoku/smaa/blob/master/SMAA.hlsl).

For temporal processing, establish scene-color and UI boundaries before choosing the final insertion point. The current present API has only color. The renderer has real depth resources and generic per-draw shader constants, but these alone do not establish a synchronized camera transform, object history or motion field. First validate camera-only reprojection on static geometry; then moving objects and skinned characters; then transparency, particles and resets. Reuse the proven contracts for TAA and later DLSS/FSR research.

FSR spatial and temporal implementations must be named separately. A color-only spatial candidate such as [FSR1 EASU/RCAS](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-spatial/) does not prove readiness for temporal FSR or DLSS. Each temporal SDK/version needs its own input units, flags, resource states, lifetime and capability checks. Optical flow can be evaluated as an approximation, but is not evidence of native geometry motion, depth or injected projection jitter.

The initial temporal investigation found these concrete starting points:

| Input | Located in this project | Next proof |
|---|---|---|
| Color and depth | Format-keyed scene resolves; `ResolveDepthOnGpu` exports D32 depth to R32. Historical screen-depth and shadow-atlas samples are distinct. | Select matching producers, valid subrectangles and frame IDs across field, battle, text and camera transitions; establish the projection convention |
| Camera and geometry | Per-draw VS constants; sampled character shaders use `c[233..236]` for final position and indexed constants for skinning | Separate pass/object/camera semantics; do not assume one shader's matrix is a universal view-projection matrix |
| Native motion | Translated vertex math and current streams/constants are inspectable | Stable instance matching, previous transforms/bones/deformation, and coverage-preserving motion output; current PSOs bind only one color target |
| Jitter | A final host-clip conversion exists alongside Xenos half-pixel correction | Apply a separate render-pixel offset only to identified scene geometry; measure the displacement and keep shadow/UI/fullscreen sampling correct |
| History and UI | Frame boundaries and selected-resolve tracing exist | One immutable temporal frame token; scene-only insertion point; reset on cuts, map loads, size/mode changes and invalid frame pairs |

Use a project-owned backward motion convention in render pixels: a surface now at `(100,100)` and previously at `(98,100)` has `mv=(-2,0)`. Convert only in the consuming adapter. For those pixel vectors, Streamline specifies normalization by render width/height, whereas direct NGX uses pixel scaling of 1. Validate each with a known translation. See the pinned [Streamline DLSS guide](https://github.com/NVIDIA-RTX/Streamline/blob/e8aaa6eaac968711fb62473d4ae8256dde20919b/docs/ProgrammingGuideDLSS.md), [common constants](https://github.com/NVIDIA-RTX/Streamline/blob/e8aaa6eaac968711fb62473d4ae8256dde20919b/include/sl_consts.h), and [NGX helper](https://github.com/NVIDIA/DLSS/blob/main/include/nvsdk_ngx_helpers.h).

Keep analytical FSR and ML FSR capability records separate. Confirm current color/exposure, motion/depth/jitter, reactive-mask and resource requirements for the selected provider rather than copying flags between versions. Query hardware support and use a tested SDK package; documentation availability does not establish distributable binaries or an enabled backend on the local GPU. See [AMD temporal FSR documentation](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-upscaler/) and the pinned [ML upscaler guide](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/techniques/super-resolution-ml.md).

Advance from static camera reprojection to moving rigid objects, then skinning and transparency. A proposed first probe is below 0.25 render-pixel reprojection error on selected visible rigid landmarks, followed by image sequences covering limbs, particles and disocclusions; this is an engineering target, not an achieved result or vendor rule. Pause the temporal experiment when inputs cannot be paired or visible regressions appear, retaining the working spatial path while fixing the missing contract. Vendor upscaling should replace the scene TAA stage, not stack a second temporal filter behind it.

### Frame rate

`gpu/command_processor.cpp` currently has a present-side `LO_FPS` cap defaulting to 30; the guest vblank producer runs independently near 60 Hz. Present count is insufficient to establish simulation speed.

The [Xenia Canary patch at a fixed upstream revision](https://github.com/xenia-canary/game-patches/blob/5c3b70e92c1c050dafd9e35a6c57e1edf4fb1a47/patches/4D5307FA%20-%20Lost%20Odyssey.patch.toml) provides a useful 60 FPS lead at `0x827B4A0C`: the immediate in `li r10,2` becomes 1. It also reports gameplay problems above 60 in that implementation. That warning does not establish a universal 120 FPS limit. Validate decoded executable bytes and function meaning for both supported editions; use a maintained recompilation hook instead of editing generated C++ or blindly applying a differently named region patch.

Prioritize stable 60 FPS with correct speed against the 30 FPS baseline. Determine which systems advance by elapsed time, frame count or vblank. If a subsystem speeds up, correct its time step or interpolation rather than globally slowing audio or all clocks. Store wall-clock, game-state and unique-frame evidence together. Test 120 FPS against these controls only as optional follow-up; defer it if difficult without blocking v0.4.0.

The static FPS audit also identified separate host DXGI vsync and a possible pacer catch-up issue after a long stall. Measure these independently of guest simulation. The current supported Asian decoded image contains `0x39400002` at the candidate instruction, and the existing USA/Europe audit uses the same decoded code image. A similarly named NTSC-J upstream patch uses another address and must not be substituted. The Xenia post-processing upscaling patch is another bounded lead; inspect its original instructions and effects before applying any equivalent change.

## Validation boundaries

The initial scope review did not modify runtime code or run the game. Later checkpoints validate native-output host text, scene AA that avoids repeating AA on subsequent UI, and experimental camera-based TAA in the recorded static and moving scenes. The 60 FPS option has completed sampled movement, dialogue/audio, Graphics-menu, static-camp and Ring core-timing/long-hold validation. These results establish the requested implementation and bounded validation; broader font and scene coverage, precise Ring release/Perfect, full-game timing, locked 60 FPS and the optional 120 FPS result remain outside that evidence. There is no new user acceptance; development remains local, unpushed and unpublished. Use selected suites from [tools/tests/README.md](../../tools/tests/README.md), extending `LoPresentationTest` only for meaningful new rendering behavior. Include compatible legacy settings, malformed input and persistence failures when the configuration schema changes. GPU readback captures establish bounded image/input evidence; their stalls must be excluded from performance claims.
