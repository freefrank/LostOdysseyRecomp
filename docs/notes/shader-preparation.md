## 2026-09-07 continued: direct extraction using known layouts (local, unreleased)

This section keeps the evidence from the `79308a15…` package and the earlier scanner. Its USA/Europe 0 / 52 and fallback status describe the old metadata, not the combined table above.

The user authorized that normal discovery no longer walks the whole package SHA256 of known CPX files. The new layout table binds known packages to their positions inside the package using the complete small FPI SHA256, the FPD file name / size, and the offset / size of each extent. Known empty packages, non-CPX extents, and duplicate profiles that were already extracted are skipped directly. For the first package containing shaders, only the header, the block table, and the independent blocks covering the required microcode are read. The package source is published only after all extracted microcode passes the hash check.

This is the extraction contract for known layouts. It is not a resource integrity check. Unread blocks, known empty or non-CPX content, and same-size modifications to skipped duplicate copies may go undetected. Unknown layouts fall back to whole-package reads and the SHA256 identity path. If the old profiles still match, the existing index can be used. Unknown content or failed extraction goes to full decoding and container search. Partial results from a failure are not marked as complete.

`LO_SHADER_FULL_SCAN=1` is an explicit diagnostic entry point. The renderer disables the bare resource, CPX package, and archive layout indexes, and enables strict mode. It runs a full resource scan every time and does not reuse the last strict manifest. The v5 manifests `resource-scanner-v5-cpx-direct` / `resource-scanner-v5-cpx-strict` separate the two modes and invalidate the old v4 manifests. Normal warm caches still use resource path / size / mtime, plus per-source hashes. This cannot detect a resource replacement that deliberately keeps the size and mtime. DXIL v21 is a separate cache layer.

## Multithreaded precompilation

`7ABDBAFD` detects the number of logical threads by default. It uses `max(1, logicalThreads - 1)` compile threads. It does not create extra threads when there are not enough tasks. If detection returns 0, it falls back to 1 thread. The current machine detects 16 logical threads and uses 15 workers. `LO_SHADER_PREPARE_SERIAL=1` is only for single-thread comparison diagnostics.

Each worker thread reads and verifies microcode on its own, translates it, and calls its own DXC instance. It writes to its own cache file. DXC library loading uses the existing call_once. The renderer cache table, statistics, and GPU object creation still run on the CP thread. An atomic queue distributes tasks. The main thread aggregates progress and loads the results after join. The file name must match the content hash, so that several aliases cannot write the same cache at once. Resource scanning is not parallelized.

Comparison with the same exe, the same 2000 microcode items, and two independent empty DXIL caches (reusing the same resource manifest, no scanning): single-thread compile stage 52664 ms, total preparation 53441 ms. 15-thread compile stage 6030 ms, total preparation 6746 ms. Total preparation was about 7.9 times faster. Both rounds had 1998 successes and the same 2 existing failures. The 1998 DXIL files were byte-for-byte identical, and they also matched the output of the previous serial version. Evidence: `out/parallel-prepare-results.json`, `out/prepare-bench-serial`, `out/prepare-bench-parallel`.

The first parallel performance copy missed the profile, so automatic save loading did not run. The test copy was stopped manually. It was used only for compile data and is not Map12 regression evidence. The game regression used another complete save/profile copy. The earlier 35-second scan data for a completely empty cache is unchanged. The 6.7 seconds must not be treated as complete first-launch time.

## Current: first-launch resource precompilation

The local `8FD77179` automatically scans the FPD resources in the `--game` directory. It extracts SDK microcode that passed container boundary, stage, and length checks. It removes duplicates and compiles them before the first frame. The development directories `disc1..4` scan the existing adjacent disc directories together. A standalone `game` directory scans only itself. There is no need to play the matching map first. It currently supports the `102a1100/102a1101` containers. It does not yet parse the inside of compressed archives or other container versions. This is not proof of full-game coverage.

The Windows window shows scan and compile counts and a progress bar. The game resumes automatically when finished. The title also shows progress. The window is handled by a separate thread. Closing the window during the scan was verified to work normally. The manifest records file path, size, and modification time. Next time, after verifying the source and microcode hashes, the resource scan is skipped. Corrupt microcode is extracted again. An invalid DXIL cache is compiled again. If preparation is interrupted, no completion manifest is written. A resource replacement with the same size and modification time cannot be detected by this fingerprint. Remove `resources.manifest` to force a scan.

## Previous stage: known microcode cache

The local build `2BD8598E` prepares the shaders that were already collected during the startup phase. The default cache is `cache/shaders` in the working directory. `LO_SHADER_CACHE_DIR` can specify another directory. At runtime, the original microcode is saved to `source`. The next startup first translates / compiles, or reads the DXIL for the matching version. The window title shows `Preparing shaders X/Y`, and it restores the title when done. `LO_NO_SHADER_PREPARE=1` skips startup preparation for diagnostics.

The runtime and offline tools share the v20 cache naming and the DXBC container boundary check. A truncated container, a wrong container length, or an out-of-range block triggers recompilation. This is not full DXIL semantic validation, and it does not guarantee repairing corrupted original microcode.

Offline preparation of captured microcode:

```text
LoShaderTool <microcode-directory> --cache <runtime-cache-directory>
```

The tool output includes DXIL and source, and the runtime can reuse them. The cache is not included in the public repository.
