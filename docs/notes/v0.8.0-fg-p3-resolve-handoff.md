# P3: exact producer / resolve / video diagnostic handoff

Baseline: `66794555c20f45b1f3201aa52c1968f81c970215` on
`feature/fg-p0-p3-foundation`, PR #69. Implementation commit: `957c833748ec32081a814c83c48d61a5cc1fe749`.
This implements the next diagnostic
slice requested by `v0.8.0-fg-p3-external-agent-handoff.md`. It does not
complete all P3 work or enable a frame-generation provider.

## Implemented path

The successful Vulkan SR continuation attaches the owned producer snapshot to
the actual promoted composite allocation and its conservative write generation.
The association is allocation-local; the existing `fgInputSnapshot` member is
not used to find the source of a final resolve. Writable transitions and
framebuffer bindings advance the generation and invalidate that allocation's
lineage, including when the texture layout has not changed.

`ResolveOnGpu` associates only a full, matching resolve with this source. It
allocates and records an independent final-resolve texture copy. The GPU slot
and bounded handoff pool retain the copy before commands reference it.
Subsequent writes to the ordinary resolved texture therefore cannot overwrite
an outstanding diagnostic's final pixels. A missing lineage, unsupported crop,
allocation failure or full diagnostic pool leaves the ordinary resolve intact.

`AcquireResolvedSurface` returns the ordinary texture and source plan as before,
plus an optional `ResolvedHandoff`. Its production implementation still calls
`NewestResolved` with the original frame/format-variant selection semantics.
It does not replace this selection with maximum write ordinal. The packet's
identity is compared against a newly constructed identity of the actual
selected `ResolvedSurface`.

`PresentFrontbuffer` passes the handoff to the production `FgPresentBridge`
after the ordinary resize/minimize preparation and source/output sizing.
Selection stages ownership only. The normal graphics queue submit and its
successful fence wait supply the presentation completion. Diagnostics never
control whether ordinary presentation is attempted. Real submission/device
errors continue to use `GpuWorkStopped`; this work does not bypass that stop.

## Exact identity and completion fields

- Renderer-lifetime owner ID, device epoch, real renderer frame and history epoch.
- Actual promoted source allocation serial and write generation.
- Selected resolve's own `writeOrdinal`, destination allocation serial and write
  generation, format variant, pitch, channel-swap flag, storage extent and write
  rectangle.
- Full `FramePlan` value, including its serial, geometry/device epoch, sizing,
  provider/quality and output description. A hash is not substituted for it.
- Actual source extent and prepared drawable/content rectangle at video selection.
- Separate checked source-copy, final-resolve-copy and normal-present submission
  serials; completion/discard/failed-wait/cancellation flags.

An internal renderer `Flush` is a command-batch boundary, not a game-frame tick.
The shared production `AdvanceAfterPublicFlush` method runs only at the end of
the successful public flush. The handoff checks that the selected resolve's
real frame precedes that boundary by exactly one and its history epoch still
matches. A single matching frame number cannot authorize a handoff.

The physical fences remain owned by their existing GPU slots/video owner.
A successful slot wait completes that slot's packet. A successful present-fence
wait can also complete earlier renderer uses because these submissions use the
same existing ordered DIRECT queue and checked monotonic submission serial.
The device epoch qualifies this observation. These are **not** provider fence
values: a future independent provider must maintain its own completion condition.

## Ownership state machine

1. A producer snapshot owns its five immutable copies; its GPU slot pins them
   before submission. Source metadata is not GPU-complete merely because copied
   commands were recorded.
2. A matching actual resolve reserves one of four live diagnostic packet slots,
   owns an independent final copy and is retained in the recording GPU slot.
3. Checked source and final submission attach their separate serials. They may
   share a batch or come from different mid-frame batches.
4. Exact video selection retains the packet before marking it selected. An
   unsubmitted recorded video path is canceled on an early return.
5. A checked normal-present submission attaches the consumer serial. Only a
   successful corresponding wait makes the staged diagnostic ready.
6. Failed waits preserve pending resources and keep readiness false. Failed
   later submits discard that later use without releasing earlier submitted
   producer work. Cut/history changes, display changes, alternative CPU/menu
   presentation, device stop and shutdown cancel eligibility without pretending
   that pending GPU work completed.
7. Existing successful fence retirement releases submitted owners. External
   leases remain counted toward the capacity until the last consumer drops
   them. Shutdown cancellation itself is not a GPU drain.

No unconditional per-frame `WaitIdle`, new submission, or CPU readback is added
to production. The extra copies are still opt-in via the existing one-shot
`LO_FG_SNAPSHOT_FRAME=N`. The default performs no snapshot copies. `UI` remains
`Unavailable`, and `PresentFrame.ProviderReady` is not used to authorize this
diagnostic path.

The new `--fg-handoff-only` option executes ten cases using the actual Renderer,
SR continuation, resolve implementation, acquisition implementation, production
video bridge, presentation shader, Vulkan commands and fences. Only the vendor
SR operation and external platform/MMIO boundary are substituted. Cases cover
same- and different-batch source/final copies; mismatched identity/plan/epoch;
reused guest addresses with different format variants; writes to the source or
final allocation; cancellation; producer/consumer failed submits and waits;
capacity exhaustion; and final lease reclamation. Positive cases read back 64
pixels from the independent final copy after the ordinary resolve was overwritten.

The fixture executes the video bridge used by `PresentFrontbuffer`; it does not
create an SDL window or execute a physical WSI present. Both complete production
renderer.cpp and video.cpp translation units are separately compiled by the
focused target. This distinguishes executable shared-path coverage from a
full-game/window test.

## Still unavailable or unverified

This slice supports the exact successful-SR promoted allocation followed by a
full matching resolve and an unscaled centered video region. Unproven later
writes, different target chains, postprocess/UI lineage, other crops/scales,
missing source plan or identity, CPU/menu uploads, and no-SR/AA/TAA/failed-SR
paths retain ordinary presentation without a diagnostic handoff.

This is not proof of real guest HUD/subtitle/battle-UI separation. Storage format
and the SR candidate's name are not color-semantic evidence. No provider/Reflex
integration, P0 probe rerun, physical displayed generated frames, full-game
relink/playthrough, Windows GPU run or user acceptance is claimed. P0 Gate 1
remains unpassed. Delivery is a source/test update to the open PR, not a merge,
release, or change to default FG behavior.
