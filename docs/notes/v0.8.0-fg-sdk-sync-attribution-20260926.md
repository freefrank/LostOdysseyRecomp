# v0.8.0 FG SDK 同步归因记录

日期：2026-09-26。范围：709e234 前台 run03 API trace 与对照运行。

## 已确认事实

run03 使用与 709e234 硬件记录相同的 executable（SHA-256 `56EB435E437BBC446E4B3D18271ACC6681B1DBA816D8A82C21F4D5CE78145BB8`），覆盖 48 帧、33 个 SDK 报告的 generated intervals、34 次 queue waits、0 次 explicit timeline waits；validation/Streamline errors 各 39，cleanup aggregate 为 1，exit 1。证据为 `out/streamline-fg-p0/709e234-hardware/run03-api-trace/`，其中 Vulkan API trace 约 45 MB。

run03 的 SDK WAW 证据位于 API lines 60547–60580：同一 `nv.sl.dlss_g.cmdCtx.dlssg.command-buffer` 中的图像 `0x2360000000236` 从 `UNDEFINED` 转为 `GENERAL`，barrier 的目标访问仅为 `SHADER_READ | SHADER_WRITE`，随后紧接 `vkCmdClearColorImage` 的 transfer write，stdout 同时记录 WAW。外围 host fence 不能补足 SDK 内部 barrier 的 access scope。

首个 clone 的证据显示：API line 57006 的 initial layout 为 `UNDEFINED`，line 57008 返回图像句柄 `0x3F400000003F4`（下文简称 `3F4`）；lines 57013、57043、57054、57170 仅记录 requirements/bind/view/name。首次布局操作在 lines 57462–57477，直接使用旧 `TRANSFER_SRC` 到 `GENERAL`，此前没有可见的 `3F4` 初始化 barrier/copy。DLSS-G command `0x74B40D0` 的实际 submit 为 API lines 62699–62714；line 62647 只是 zero-command signal submit，不能作为实际 clone submit 证据。stdout lines 213/226 记录对应 VUID。

当前最精确的归因是：SDK clone 的初始布局与首次 barrier 的 oldLayout 不一致。仍不能区分是 SDK 漏掉初始 transition，还是 SDK state cache 错误。仓库可见 SDK source 只有 wrapper.cpp，没有 clone/dlfg 内部实现，因此没有已证实的 host-side 修复点。

run04 仅设置 `DISABLE_RTSS_LAYER=1`，仍注入 `RTSSHooks64` 并记录 36 errors；它没有隔离 RTSS，不能用于归因。用户已自行禁用 RTSS 并停止该分支，本记录不再建议继续排查该软件。

探针当前只增加 `blocked_by_session_errors` 与 `missing_completion_signal` 诊断计数；守卫、同步和返回码没有改变。该纯日志改动未重新 build 或实机验证，不能扩大现有结论。

## 边界与后续

以上结果解释了前台 run03 的 SDK hazard 位置，但不证明 host 可修复、FG 同步已修复、生成帧已显示或 P0 Gate 1 已通过。UI 诊断按用户优先级暂挂，默认 FG 与 provider 生产路径保持关闭。

官方 Streamline sample `v2.14.1`（commit `0bb8bf3ee80ce8d6b53688c2e237ac0981ce2f6c`）已独立构建。第一次仅修正 CMake 配置、未改运行代码的 debug 运行以 `0xC0000005`（`exe+0x421b`）退出；隔离补丁 `tools/tests/streamline_fg/official_sample_validation.patch` 另补齐 validation wrapper 下的 device 获取、`independentBlend`、`privateData`、`deferred_host_operations`，不能当作上游 sample 已通过。补丁构建退出 0（可执行文件 SHA-256 `1445D1CD3E490BBBEA909F2492AA5AA04F55BD5BD7C708CB00F02A0816A5441E`）后，在 `out/streamline-sample-v2.14.1/run02-minimal-fix/` 以 `-vk -debug -sllog -logToFile -DLSSG_on -maxFrames 100` 运行正常退出 0；log 1066 报告 interpolation enabled，1112/1114 复现 clone 初始 `UNDEFINED`、预期 `TRANSFER_SRC`，1124 复现 pacer semaphore 提前复用。这与 LO probe 的 SDK 迹象一致。sample 自身的 GBuffer clear 和 teardown errors 单独记录，不能并入本记录的错误计数；没有 validation-clean、生成帧显示或物理显示验收证据。由此只能确认这些现象并非 LO probe 独有，不能据此证明 SDK 已修复或 host 可修复。

规范依据：[Vulkan access flags](https://docs.vulkan.org/refpages/latest/refpages/source/VkAccessFlagBits.html) 将 shader write 与 transfer write 定义为不同访问类型。
